# 查询与 Chunk 稳健性修复说明

核验日期：2026-11-14。修复与性能验证的基线为 `db6ca87971109d7195e35a96b7410cafcd04db63`，本文说明随修复代码一同归档。

原始两个提交的改动分类、代码对照及性能实测见 [审查报告](审查报告.md)。本说明记录随后落实的修复、验证结果和适用边界；原报告中的测试数量和生命周期描述属于初次审查时点。

## 结论

已处理可复现的错误结果、共享值破坏、非法枚举状态、失效查询结果访问，以及持续增删导致普通原型不断增加 Chunk 的问题。压缩过程的异常退出也会使旧借用失效。

“通用”有边界：这些改动使现有 API 在更多负载和异常路径下成立；不同共享值不能合并、已返回的裸引用不能自动撤销、并发结构修改需要同步，这些约束仍然存在。没有把所有负载强行改成一种布局，也没有宣称消除全部潜在漏洞。

最终 ECS 测试为托管、原生后端各 **615 项通过，0 失败、0 跳过**；NativeTranspiler **383 项通过**。原生测试明确要求加载当前 HEAD 构建的 DLL，未用静默托管回退冒充原生结果。已有编译警告仍存在。

## 原写法、劣势与修复

| 问题 | 原写法与劣势 | 当前实现及理由 |
|---|---|---|
| 普通原型持续增删 | 删除后保留 Chunk，新增只查看最后一块；前面的空位闲置。固定存活量也可能不断分配块 | 保存首个可能未满块的扫描游标，新增从该位置寻找空位，删除时回退，压缩及清空时重置；复用现有存储，避免每次新增从头扫描 |
| 查询借用失效 | 仅在跨 Chunk 时检查；块内 MoveNext、Current 及保存的结果属性可能继续返回已失效地址 | 每次 MoveNext、Current、结果属性访问均检查同一借用标记；双组件和生成的多组件实现一致 |
| 初始 Current | 双组件偏移初始为 -1，恰好通过“负数表示有效”的条件，基址仍为 null | 初始偏移设为 0，沿用已有状态机拒绝未开始的枚举，首次推进仍正常进入首块 |
| 默认结果 | 默认 token 和指针没有明确初始化状态保护 | 受跟踪入口拒绝默认 token；双组件结果校验首列指针，保留公开裸指针构造的调用方寿命契约 |
| Changed 过滤 | 静态计划已去除动态条件，整表快速路径仍直接按计划启用，绕过本次 Changed 条件 | 仅当本次枚举没有 Chunk 动态过滤时启用整表路径，复用现有游标过滤，不在每实体循环重复解析过滤 |
| 共享组件压缩 | 只判断目标有空位；搬入不同共享值的块会改变实体读到的值，目标满后也可能误入另一组 | 首次选目标及后续切换目标均检查完整共享值组合；托管共享值比较已有索引，值类型沿用项目已有的装箱相等语义 |
| 压缩异常退出 | 查询失效只在成功结尾执行；先移除空块，再因共享值比较异常退出，旧查询仍可通过校验 | 在 finally 中使查询失效，覆盖成功与部分完成后的异常退出；保留已经完成且一致的搬移和块移除 |

扫描游标只有一个整数；没有加入另一份空块集合或删除时的分配。游标之前的块均已满，删除使它回退到更早的可能空位。压缩会交换块的位置，所以在开始压缩该原型前重置。批量清空也重置，下一次创建从头查找。

共享原型指定值的创建继续走现有共享值匹配器。未指定共享值的入口继续使用末块分组，避免把未指定值的实体任意放入较早的另一共享组。因此“普通原型固定存活量不再因这种增删模式不断增块”，不能扩展成“所有共享值负载内存固定”。

查询状态继续区分结构版本与关系版本。结构变化使两类借用失效，关系重定向只使跟踪关系的借用失效；普通查询结果不会因单纯关系重定向失效。可写访问保留关系只读约束和 copy hook 写保护。

## 红方场景与蓝方验收

| 攻击或边界场景 | 验收结果 |
|---|---|
| 固定 128 个活跃实体，每轮删除再创建 1 个或 64 个，共 40 轮 | 块数维持 2，逐轮检查实体定位和 slab 不变式 |
| 清空、压缩交换块后再次批量创建 | 游标能重新找到空位；实体数量、块数、定位、slab 账目一致 |
| 保存双、三、四组件查询结果后执行结构变更 | MoveNext、Current、只读和可写结果属性均拒绝失效借用 |
| 保存查询结果后释放 World | 访问抛出 ObjectDisposedException，拒绝返回失效引用 |
| 关系重定向 | 关系过滤结果失效，普通结果继续可用 |
| 默认查询结果、未开始或已结束的枚举 | 拒绝访问；有效裸指针构造的双组件结果仍可读写 |
| Changed 条件清空、写入、再次清空，跨两个原型、2/3/4 元组宽度 | 返回数分别为 0、1、0，与 Chunk 入口一致 |
| 不同值类型或托管共享值、多个共享列组合、重复压缩 | 共享值保持原样，只有完整组合一致才合并 |
| 目标块填满后遇到不同共享组 | 跳过不兼容目标，不丢失尚未搬出的实体 |
| 移除空块后，共享值 Equals 抛出异常 | 旧结果失效；保留实体的共享值、位置表、slab 均一致；后续压缩和新查询可继续执行 |

最后一例先运行失败测试：压缩确实移除了空块，但旧结果属性未抛异常。加入 finally 失效后，通过最终全量复验。记录为 `evidence/review-followup-compaction-exception-red.log`。

初期新增测试的红灯日志为 `review-followup-red.log`，其中一项失败来自测试把容量设成 2，而运行时最小容量实际为 64；不能把这项计作独立代码漏洞。最终测试改用容量 64，并真实填满一块，覆盖同值跨块合并及目标填满后的切换。

## 实际运行与性能成本

本轮比较的基线是未修改的当前 HEAD `db6ca87`，修复侧为工作区当前实现；与原始审查的 `f75849e → ee4cd72` 测量分开。基线放在独立工作树，未改动当前工作区来回切换版本。

环境：Windows x64、.NET 8.0.30、16 个逻辑 CPU、明确选择托管后端、调度器 2 线程、Release、`DOTNET_TieredCompilation=0`。每侧 3 个进程，顺序为旧/新、新/旧、旧/新；进程内测 12 轮，排除前 2 轮。单位为 ns/实体，表中每格是三个进程各自的中位数。

结构变更每轮 50,000 个实体，创建 A/B、添加 C、移除 C、销毁。校验值每个进程均为 14,999,700,000，实体定位检查在计时外执行。

| 操作 | 基线的三个进程 | 修复后的三个进程 |
|---|---|---|
| 创建 | 41.68 / 40.50 / 42.62 | 38.41 / 38.94 / 41.19 |
| 添加组件 | 92.16 / 87.23 / 92.26 | 84.60 / 86.41 / 93.17 |
| 移除组件 | 73.81 / 74.92 / 87.18 | 73.89 / 78.27 / 78.12 |
| 销毁 | 31.55 / 30.27 / 32.96 | 30.13 / 40.61 / 34.42 |

这些结构操作有明显波动，不据此宣称本轮修复普遍提速或零成本。更明确的结果来自持续增删探针：容量 64、128 个存活实体、20 轮替换 64 个实体，三个基线进程压缩前均为 **22 块**，修复侧均为 **2 块**；显式压缩后均为 2 块，定位错误均为 0。

查询测 100,000 个 A/B/C 实体，每轮重复 32 次。双组件执行 `A += B`，三组件执行 `A += B + C`，另用 Chunk Span 执行相同计算。每个进程每条路径的结果和校验值均相符。

| 查询入口 | 基线的三个进程 | 修复后的三个进程 |
|---|---|---|
| 双组件实体 Query | 1.232 / 1.010 / 1.022 | 1.675 / 1.833 / 1.728 |
| 三组件实体 Query | 0.708 / 0.682 / 0.721 | 1.970 / 1.767 / 1.836 |
| 双组件 Chunk | 0.528 / 0.421 / 0.454 | 0.468 / 0.380 / 0.433 |
| 三组件 Chunk | 0.560 / 0.661 / 0.622 | 0.927 / 0.551 / 0.576 |

逐次借用检查在这个简单标量负载下有明显成本，三组件生成结果从不校验改为校验后尤其明显。保留此成本，是为了在现有托管查询入口拒绝失效地址。结构稳定的批量计算可以使用已有 QueryChunks，获取列视图后在 Span 上循环；该路径同样要求循环期间存储有效。

这不是逐项消融实验，不能把全部差值精确分摊到某一次校验。没有固定 CPU 亲和性或运行 BenchmarkDotNet，也没有测原生查询、真实游戏系统、Linux、ARM64、ASan 或 TSan。跨构建计时和短循环受 JIT 布局、系统负载影响，尤其不能据此给出跨 ECS 排名或最坏延迟保证。

探针完整入口保存在 `evidence/FollowupProbe.cs.txt`，查询内核在 `evidence/QueryCostProbe.cs.txt`，项目模板在 `evidence/FollowupProbe.csproj.txt`。将两份源码另存为 Program.cs 与 QueryProbe.cs，放到仓库的 `tools/EcsComparison/obj/followup-probe`，模板另存为 Probe.csproj；模板相对引用当前仓库 ECS 和源生成器。构建后直接运行 Probe.dll；增加任意命令行参数即运行查询探针，无参数运行结构变更与持续增删探针。

以下约束仍是当前设计的一部分：

- 属性已经返回的 ref、Span 和裸指针不能自动撤销；检查与解引用之间也不是并发锁。结构写入与使用这些引用必须分阶段或通过现有调度和同步机制协调。
- 不同共享值组合需要独立存储；大量不同组合会占用大量块。显式压缩归还空块及空 slab，复用空位不会直接把 slab 归还系统。
- 共享值比较沿用现有 Equals 语义；值应在作为共享值期间保持稳定。装箱比较可能分配，压缩没有“零分配”承诺。
- 压缩异常保证已完成搬移的定位与借用失效，未提供整次操作回滚；后续可在修正比较异常后继续压缩。
- 位置编码容量上限、类型掩码大小、批处理阈值和硬件布局仍是有界策略。当前已有边界检查及回退的部分继续沿用，未为了追求无条件通解添加额外配置、抽象或存储后端。
- 未完成任意用户回调、分配失败和所有并发交错的全局证明。测试证明上述具体场景，不能证明不存在其他缺陷。
