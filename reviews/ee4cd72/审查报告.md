## 三处问题：红方复现、蓝方修复

### 1. [P1] Changed 条件被快速路径绕过——已有缺陷，新路径仍不正确

**触发方式：**先创建两种 Archetype 的实体，清空 Changed 位，再枚举带 `WithChanged<Position>()` 的 2、3、4 组件查询。期望 0 个，修复前仍返回实体。写入一个独立 Chunk 的 Position 后应只命中该 Chunk，再清空后应回到 0 个。

**新版原因：**`EntityManager.QueryCache.cs` 在创建可复用 Archetype 计划前移除 Changed 条件、动态 Shared 值、关系目标和数量限制。这种拆分本身合理：静态类型匹配可缓存，动态条件应由本次枚举执行。但 `QueryTraversalCursor.CanUseChunkTable` 只读取缓存计划的标志；计划已看不到 Changed，导致枚举器直接走 Chunk 表，跳过动态过滤。

修复前后真实代码：

```csharp
// ee4cd72，修复前
public readonly bool CanUseChunkTable => _plan.CanUseChunkTable;

// 当前修复
public readonly bool CanUseChunkTable => _plan.CanUseChunkTable && !_hasChunkFilter;
```

`_hasChunkFilter` 来自本次 builder 的 Shared/Changed 条件。判定发生在选择枚举路径时，不向每个实体的循环增加过滤分支。

**旧版归因：**复核旧版 `QueryEnumerable.cs` 后，用同一份 5 用例查询回归测试在 f75849e 实跑：Changed 的 2、3、4 组件用例均失败，两个 Current 状态用例均通过。不能把 Changed 错误写成 ee4cd72 首次引入。

**影响：**增量系统会处理不应命中的实体；是否造成业务错误取决于下游是否允许重复执行。不是访问控制绕过的证据。

**边界：**当前 Changed 机制按 Chunk 的变化状态筛选，不承诺逐实体、逐组件精确差分。回归测试把不同变化放到不同 Chunk，避免把现有语义误当成更精确的跟踪。

### 2. [P1] 未开始枚举时 Current 返回非法指针结果——本次新增回归

旧版 `Current` 在当前 Chunk 的内存地址为空时抛出异常。新版改用相对区间末尾的偏移判断有效性：有效实体的 `_slotOffset` 必须为负，0 或正数表示无有效实体。

但是新版构造器把偏移初始化为 -1，同时把两个组件基址初始化为 null。还没有调用 `MoveNext()` 就读取 Current，会通过“负数有效”的检查，返回由空基址加负偏移形成的指针结果；继续访问组件存在非法内存访问风险。

```csharp
// ee4cd72，修复前构造器
_slotOffset = -1;

// 当前修复：与 ResetRange 的无效状态一致
_slotOffset = 0;

// Current 原有判定保持不变
if (_slotOffset >= 0) throw new InvalidOperationException();
```

**为什么这样修：**把初始状态纳入已有状态机即可，不需要在每次 Current 增加指针判空或额外状态字段。首次 MoveNext 仍会进入取 Chunk 的路径，不丢第一个实体。

**验证：**有过滤和无过滤各一例，覆盖初始 Current、首次读到值 42、结束后的 Current、重复调用 MoveNext。红方只检查非法结果是否被拒绝，不解引用非法指针来制造进程崩溃。旧版两例通过，目标提交修复前两例失败，修复后两例通过。

此风险的严重性来自 unsafe 指针；标准 foreach 不会在首次 MoveNext 前读取 Current，常规使用并不必然触发。

### 3. [P1] CompactChunks 混合不同共享值——已有数据破坏缺陷

共享组件值属于 Chunk，而非每个实体独立存储。原来的 `FindFirstChunkWithRoom` 只看剩余容量；`MoveEntitiesTo` 在目标满后也只寻找下一个未满 Chunk。实体从 Material=8 的 Chunk 搬到 Material=7 的 Chunk 后，读到的材料会无声变成 7；托管共享资源也一样。

旧版单文件 EntityManager 中同样只检查容量。这不是本次提交新增的问题，但新版把压缩作为内存回收入口，实际使用频率和后果更值得检查。

修复前：

```csharp
if (span[j].EntityCount < span[j].Capacity) return j;
```

修复后：

```csharp
if (span[j].EntityCount < span[j].Capacity
    && SharedValuesMatch(span[limit], span[j])) return j;
```

还同步修复了“首个兼容目标满后，跳到下一个不兼容目标”的路径。只修第一处查找是不完整的。

**匹配规则：**遍历该 Archetype 的全部共享组件；托管共享值比较已有存储索引，blittable 共享值复用项目的 `ReadBlittableSharedBoxed` 和值相等逻辑。必须整组相同，不能只比较某一个 Material。

**代价：**共享值比较增加压缩成本，blittable 值读取有装箱，因此删除了此 API 注释里“零分配”的保证。没有为了这个冷路径新增通用缓存或重写共享值机制。

**红方：**相同 Material/Mesh 应合并；不同 Material 不应混合；相同 Material 但不同 Mesh 也不应混合；首个目标填满后要跳过不兼容目标。修复前 4 例中 3 例失败。蓝方修复后全部通过，同时检查重复压缩、实体数量和定位表一致性。

### 位置打包的硬边界

真实代码使用 `Address >> 16` 读取 ChunkIndex。因为是有符号算术右移，高位只能使用正数区：

- 每 Chunk 容量最多 65,536，槽号 0..65,535。
- 每 Archetype 最多 32,768 个 Chunk，块号 0..32,767，并非 65,536 个。
- `ClearLocation` 把 Address 写成 -1，读到 ChunkIndex=-1、Slot=65,535；存活判断依据 Archetype，不能靠 Slot 是否非负。
- 建立容量和分配边界存在校验；底层公开 SetLocation/字段不是面向不可信输入的校验接口，越界会截断。

现有测试覆盖打包和边界计算，本次没有真正分配 32,768 个 Chunk 做资源耗尽验证。持续增删又不压缩会更早碰到 Chunk 数量限制，即使活跃实体很少。

### 保留空 Chunk 为什么有实际代价

新版普通创建只检查末尾 Chunk，没有对前面所有空洞进行填充。销毁旧实体留下前部空块，再在末尾创建，就能不断增加保留块数。

实跑固定容量 64，先创建 128 个实体，再循环 20 次：FIFO 销毁 64 个、补建 64 个。结果：

| 版本 | 活跃实体 | 压缩前 Chunk | 压缩后 Chunk | 定位错误 |
|---|---:|---:|---:|---:|
| f75849e | 128 | 2 | 2 | 0 |
| ee4cd72 + 本次修复 | 128 | 22 | 2 | 0 |

这不是实体泄漏，而是 Chunk 保留策略；长期不压缩时并不等于内存会自行稳定。此次没有擅自引入自动压缩、空闲 Chunk 索引或每次创建扫描空洞，因为这些会改变提交刻意选择的热路径成本。当前最小落地是修好压缩正确性，并写清安全点调用要求。若业务要求内存随活跃实体量有界，需要另行选择回收策略并重测性能。

### 生命周期约束确实变弱，不能当成免费优化

旧版双组件 Current 先 `_readState.Validate()`，结果也携带读取状态。新版双组件 Current 仅检查偏移，结果直接持有指针；区间内 MoveNext 直接返回，失效检测发生在边界推进。

因此在同一 Chunk 中枚举时销毁实体、修改结构或 Dispose World，再访问当前结果，不能指望下一次 Current 立即抛异常。组件指针可能已经失效。现有契约将这种用法排除在支持范围外；这属于需要调用方接受的设计取舍，不是本次偷偷补一个判断就能全部解决的问题。返回的 ref 也无法在每次后续读写时自动验证。

支持的使用方式是在遍历期间记录 ECB，结束读取并完成相关 Job 后，在结构安全点回放；不要跨结构变更保存结果、Span 或 ref。需要强制防御不正确调用的 SDK，应重新设计检查策略，并接受相应成本，不能用这轮基准为取消检查背书。

| 托管到原生回调 | 托管异常可能跨 unmanaged ABI 边界 | 回调捕获异常，分配失败返回 null | 调用方仍须处理 null；吞异常不等于分配成功 |
| 原生加载 | 不匹配 DLL 的能力可能在较晚调用时才暴露 | 校验 ABI 和必需的 RegisterAllocator 导出，不符合则回退托管 | 回退会改变性能，测试必须确认实际加载后端 |
| 提交与关闭竞争 | 生产者发布和 shutdown 排空之间需要明确顺序 | 关闭发布门、等待生产者、再排空；相关原子使用 seq_cst | 仅有代码审查及 Windows 测试，不能声称已覆盖所有弱内存序平台 |
| WaitIdle | 仅看部分队列／活跃状态可能漏掉发布中的任务，worker 等待自己也可能死锁 | pending 在发布前增加，释放后减少；等待结合 pending/active，处理 worker 自等待 | 正确性依赖全部成功／失败／取消路径平衡计数 |
| worker 唤醒 | 检查队列、进入休眠之间可能丢唤醒 | wakeEpoch、parkedWorkers 顺序约束与退避唤醒 | 本次并发专项通过，不等于形式化证明或压力测试穷尽 |
| 批次失败清理 | 提交中断后需要归还 backend 计数及引用 | AbortSubmittedBatch 平衡资源，调度器缺失时避免紧密自旋 | ReleaseState 的 previous==0 防护不能证明任意悬空指针重复释放都安全 |
| 调试 HTTP | World 自动启动静态服务，后台读取运行中的世界 | 显式创建实例，仅 localhost；调用方安全点 Publish JSON 字节快照，HTTP 只读快照 | 不是带认证的远程管理服务，也不能 Publish 时与结构写入竞争 |

调试接口行为也有变化：GET 已发布世界返回 200，未发布返回 503，未知路径 404，非 GET 返回 405。默认不自动启动减少暴露面，快照发布把 HTTP 线程与 ECS 内存读取隔离；这比在 HTTP 回调中直接遍历活跃世界更容易维持线程边界。

## 哪些主要是重构或工具改进

- EntityManager、Archetype、ChunkJobScheduler、ECB、查询选择拆为 partial 文件，降低单文件规模。责任划分更清楚，但不能独立记作性能收益，也不自动保证单一职责。
- 查询缓存从 World 集中到 EntityManager，使显式查询与 foreach 共用匹配注册表；避免两套同义缓存实现。
- 关系克隆／变更拆为准备和应用阶段，保留共享组合目标预留、容量准备及失败处理。不能把已有的准备／回滚机制都写成这次新增的事务保证。
- ScheduleGraph、SystemRunner 的相当部分是抽取代码。旧版已有确定性边排序和去重，不能据此宣称修好了旧版不存在的排序缺陷。
- EcsComparison 扩展 Arch、Unity、Query、Chunk Job、原始 Chunk 等矩阵，以及 CSV、环境信息和脚本。这提高可测性，不是产品路径本身变快的证据。
- CI 增加原生掩码、ABI、分配器相关检查。构建工具链与生成代码共同决定兼容性，不能只更新其中一个产物。

## 实跑性能证据与可复现范围

原工具 `tools/EcsComparison` 构建被缺失的子模块文件 `src/NativeDll/thirdParty/imgui/imgui.cpp` 阻断，记录在 [review-benchmark-build.log](E:/GODOT/Project/EntJoy/reviews/ee4cd72/evidence/review-benchmark-build.log)。没有伪称复现了文档里的 Arch 对比，也没有修改生产构建来绕过它。

改用完全相同的独立探针，分别引用旧版本和目标版本加本次修复的 ECS 库。源代码保存于 [Probe.cs.txt](E:/GODOT/Project/EntJoy/reviews/ee4cd72/evidence/Probe.cs.txt)。

条件：Windows x64、.NET Runtime 8.0.30，环境报告 16 个逻辑处理器；Release/net8.0；强制托管后端，调度器初始化为 2。每轮 50,000 实体，共 12 轮，前 2 轮不计入统计；单进程对余下 10 轮取中位数。关闭分层编译 `DOTNET_TieredCompilation=0`，三组进程顺序为旧/新、新/旧、旧/新，再取三个进程中位数的中位数。

每轮使用预解析的 A/B 类型创建实体，添加含 Value=i 的 C，移除 C，然后销毁。计时外核对 C 的总和与定位表；每次总和均为 14,999,700,000，与预期一致。没有仅比较空循环或只凭测试通过判断业务正确。

六份原始记录为 `evidence/review-probe-{old,new}-{1,2,3}.log`。日志里的 NativeDll 查找提示发生在强制切换之前，随后打印 `native=False`；这是明确选择的托管测量，不是把原生失败回退当成原生成功。

复现方法：用相同探针建立两个临时 net8.0 Console 项目，AllowUnsafeBlocks=true，ProjectReference 分别指向两工作树的 `src/EntJoy.ECS/EntJoy.ECS.csproj`。将 Probe.cs.txt 复制为各项目 Program.cs，Release 构建，设置上述环境变量后直接运行生成的 Probe.dll。源码中同时包含固定活跃实体的增删／压缩实验。

限制：未固定 CPU 亲和性；不是 BenchmarkDotNet 统计报告；组件简单，无观察者、关系、共享值及 Job 并行负载；同一 World 多轮复用会受新版 Chunk 保留影响。关闭分层编译减少本轮测量波动，但不代表产品默认运行方式。数据只证明这个受控场景的整组改动收益，不能推出一般业务帧时间、最坏延迟或每个局部优化的百分比。

## 没有确认或没有覆盖的事项

- 未复现交接文档中的 Arch 数值；检查了交接文档、比较工具及其构建，原始 `tools/EcsComparison/obj/struct-amend.txt` 未找到。不能据旧文档断言当前“追平 Arch”。
- 不同布局／容量条件下的快照分配数不能直接相除归因；没有复现这些实验的统一配置。
- 没有逐项消融、完整反汇编或硬件性能计数器数据，因此不能确认“某几纳秒必然来自冷页”“入口开销已不可减少”等强归因。
- 没有运行 ASan、TSan、Linux、ARM64，也没有做真实 32K Chunk 资源耗尽实验。Windows 上并发测试通过不自动覆盖这些平台。
- 未把 Query limit、任意分配失败后的全局事务性等未经复现的猜测列作已确认漏洞。
- `QueryBorrowVersion.Borrow` 单看内部方法似乎可在 Dispose 后建立 token，但支持入口 `EntityManager.GetQueryBorrowVersion` 会 CheckDisposed；未发现可按受支持 API 复现的该问题，因此未报。
- 未将不受支持的跨结构变更持有 ref、快照或游标用法伪装成已修复的内存安全保证。若产品要支持这种调用方式，需要改变公开契约和实现。

## 是否采用：按业务约束判断

这组优化适合 Chunk 较密集、类型 ID 常用且较稠密、读取阶段与结构写入阶段明确分离、允许在安全点压缩的 ECS。缓存静态匹配、把不变信息提到循环外、使用紧凑布局、冷路径分离，是可推广的做法；具体布局位数、阈值 8、内联 1,024 位掩码、边界借用检查、保留所有空 Chunk，则必须服从实际负载。

本次最重要的约束是：先保持筛选语义、共享值和生命周期成立，再衡量减少了多少工作。只看 ns/实体而忽略 Chunk 保留、错误检测范围和容量上限，会把有条件的性能收益误当成通解。
