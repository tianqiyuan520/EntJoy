## 4. 分析（读数 → 推断链条）

1. **A 侧粒度成本高度可复现，且与 B 无关**（T6）：`f64/def = 1.1093`、`f1/def = 1.7878`，各 6/6 同号，**逐对散度仅 ±1%**
   ⇒ EntJoy 的成本对"工作项数"是**确定性函数**，不是噪声 ⇒ 任何 <2 ms 的改动都**应当用这条 A-vs-A 口径定案**，而不是跨栈比值。
2. **单位成本可从两个独立器械对齐**：Melee 是单 dispatch、n=10⁶，f64→f1 = (166.72 − 139.11) ms ÷ (10⁶ − 15,625) 工作项
   = **28.0 ns/工作项**；而空体器械 `SchedTileBench`（§7(l6)(b)，同 DLL、len 7936、8 worker）测得 **27 ns/tile**、每-job 地板 1.22 µs
   ⇒ **该轴是"调度器每工作项固定开销"，与内核计算量无关**。
3. **分段敏感度差异**（T7 的 `f1/def`）：`markdead 12.91×` > `integrate 7.74×` > `build 3.75×` > `flow 2.11×` > `melee 1.35×`
   ⇒ **短体 job 的相对涨幅最大**（固定开销占其总量比例大），**Melee 最小**（内核计算量绝对主导）。
   这解释了为什么"全局调细"会先打崩 MarkDead/Integrate/Flow，而 Melee 反而还算稳。
4. **Build 是例外，且这条否证了 §7ar(f) 的预期**：T7 中 Build 的 `f64/def = 0.99`（4.97 vs 4.92，Δ −0.05）
   ⇒ **Build 的赤字不是工作项数**（是原子 RMW 争用 + 散列写，§7ar(k)/(3)）
   ⇒ **"给 Build 两趟显式 innerBatch ⇒ −1.2~1.7 ms"的预期作废**；Build 的量在**认领形态**（同粒度下切片 4.09 → 2.88）。
5. **Unity 承受得住它自己选的最细粒度**（T3/T8）：同一个 Unity 二进制 18 次运行只在 **158.3~178.8（max/min 1.129）** 之间漂，
   而它对 Melee/MarkDead/Flow/AliveBit 传的 `0`（比 64 更细）下，Melee 稳定在 **120.5~137.0**、Build（显式 64）**2.65~3.02**。
   对照：EntJoy 一旦被强制到同一最细档就 **+79.8%**（T5）⇒ **差距在"每工作项成本"，不在峰值/噪声**。
6. **两条口径的裁定**（T5/T8）：
   - **纯框架 / 等 BatchSize / 无 JCC**：Build **1.74×**（T8 `0.574`）、(k) 1.87×、空 job 微基准 1.91× ⇒ **EntJoy 落后 1.7~1.9×**；
     Flow/薄批打平；Melee 在 A 更粗的前提下仍慢 6.8%（T8 `0.932`）。

### 7.1 为什么它**默认关**（三层原因，回答"这种为何没开启"）

> 前提澄清：**它不是"没验证就关着"** —— 它是被当作通解候选**实现并打开验证过**的，
> 提交 `16db823` 的标题就是「切片认领 + 空手才窃取**通解候选（默认关；游戏内否证全局打开）**」。

1. **全局开在墙钟上净亏**：6 对的收益侧 = Build −1.94(6/6) + Flow −0.76(5/6) + Integrate −0.14(5/6) = **−2.84**，
   但代价侧 Melee **+3.76(0/6)** ⇒ 整步 **+0.64（1/6，更差）**（3 对那轮 +3.08）。
   量级原因是**占比**：整步 161 ms 里 **Melee ≈ 121（75%）、Build 只有 ~3%** ⇒ 牺牲 3.76 换 1.94 是净亏。
   与 `ENTJOY_CLAIM_BLOCK` 同型（Build −0.69(10/10)，但 Melee +3.97、整步 +6.85(0/10)）。
2. **开关天生是"全局"的，没有"只给 Build"这扇门**：三层都只看一个全局 bool，`BatchState` 里虽有 `funcHash` 但切片分支不看它 ——

   - `JobSystem_Tiles.cpp:1479`（`InitSliceCursors`）：`if (!g_claimSliceEnabled || end == 0) { sliceCount = 0; return; }`；
   - `ChaseLevScheduler.cpp:651`：执行侧只看 `batch->sliceCount > 0 && end > 0`。
   ⇒ **当年即使已知"只给 Build 就对"，现有开关也无法表达** —— 只能整开或整关。**这正是"按 job 给认领形态"（形态 3）要补的那段代码。**
3. **默认档纪律**：默认档必须"自证机理 + 6 对五段全看 + ≥5/6 同号"；切片在 Melee 上 **0/6**，直接不满足。

   全局默认会让性能随该 job 的空间复用形态摆动。

**它现在的三重身份（所以没白做）**：① 器械（开启时打 `[CLAIMSLICE] on` 取证横幅、可复跑）；
② **已证实根因的对照臂** —— "相邻 tile 交给同时刻不同 worker ⇒ 争同一条 cell 计数器 cacheline"这条根因，
正是靠它 + `ENTJOY_TILE_STRIDE` 一起坐实的（去掉原子后 Count 与粒度无关；打乱 index 序后原子项 1.25→0.27）；

**均匀负载上切片让 EntJoy 在任何粒度都≈Unity**（夹具 62/977/15625 tiles 全 2.44~2.55 ms vs Unity 发布档 2.62），

**判定：H1（负载均衡/尾部）被三条独立证据否证**

1. **粒度不敏感**：切片对 Melee 的亏损在 **19 tiles 时 +7.06、512 tiles 时 +6.96**（各自 vs base）⇒ 若是"静态分段造成的尾部，"

2. **worker 不是在"等"**：E1 的 aggregate `busy_ratio` **slice 反而更高**（0.9045 vs 0.8896；细粒度 0.9128 vs 0.8918）

3. **每-worker 离散度与亏损不对应**：spread(base) 0.059 / slice 0.064 / stride **0.067** / base150 0.054 / slice150 0.056

**真正对应的是"tile → worker → 时刻"的映射（顺序/局部性）**

| 变换 | Melee Δ | Build Δ | 读法 |
|---|---|---|---|
| `slice`（8 段互不相交，段内仍顺序） | **+7.06（0/5）** | **−2.09（5/5）** | 把 worker 分到 8 个区域：Melee 亏、Build 赚 |
| `stride`（**只**置换顺序；认领代码与 tile 数都不变） | **+13.84（0/5）** | −0.52（4/5） | **顺序单独就是 Melee 最大变量（≈slice 的 2×），对 Build 几乎无效** |
| `base150`（顺序不变、只把粒度改细） | **+13.97（0/5）** | −1.06（5/5） | 细粒度本身对 Melee 纯亏（与 §7ar(i) 一致） |

**⇒ 对 §7/§7.1/§7ar(e) 原解释的修正（重要）**

- Melee 的成本由 **"邻居表 / cell 计数器的缓存复用"** 支配：默认路径让 8 个 worker **沿同一条 index 轴、按到达顺序**推进（彼此空间邻近 ⇒
  共享邻居表与计数器的 cache 足迹）；一旦把 worker 分散到互不相交的区域（`slice`）或打乱顺序（`stride`），复用被破坏、每元素实耗上升 ⇒ **Melee 亏**。
- 而 **Build 的成本由"相邻 tile 争同一条 cell 计数器 cacheline"支配** ⇒ 把 worker 分开是**收益**（`slice` −2.09 5/5；
  而 `stride` 对 Build 无效 ⇒ 收益来自"**分开**"而不是"顺序"）。
- ⇒ **同一个属性（空间连贯性）对 Melee 是收益、对 Build 是成本，符号相反** ⇒ **不存在全局旋钮**，必须按 job 给认领形态。
  这也**解释了夹具 skew 模型为何误判**：它只建模了"每元素成本方差"，**没建模空间复用**。
- ⚠ 精确微机理（L1/L2/L3 vs 硬件预取 vs DRAM 带宽）**本机无 PMU，不做进一步断言**（沿用本仓既有边界）。

**器械**：`tools/gate-run/ab-slice-mech.ps1`（5 臂 × 5 对）、`parse-slice-mech.ps1`、原始 `slice-mech-run.txt`。
⚠ 器械坑（本轮踩到）：**`[E1]` 诊断输出走 stdout**，不在 Godot 的 `--log-file` ⇒ 解析必须读 `A-<arm>-r<n>.stdout.txt`。
