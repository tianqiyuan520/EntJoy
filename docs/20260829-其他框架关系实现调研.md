# 其他框架关系实现调研（2026-08-29）

> **目的**：对比 Bevy 0.16+ / Flecs / Unity 的关系实现，评估 EntJoy 关系系统（S23/S24）的设计差距与可借鉴点。
> **结论先行**：EntJoy 的"关系 = 组件列 + RelationSlot 值"设计与 Bevy 0.16 的 non-fragmenting 思路一致（target 存组件值，不拆 archetype）；差异在反向索引维护方式（Bevy 用组件 hooks，EntJoy 用主动 RelationIndex）。

---

## 一、Bevy ECS 0.16+ Relations（调研完成，基于官方源码）

### 1.1 存储：两个普通组件配对（不是 sparse set）

```rust
// source 实体上：关系的"事实来源"，值内嵌 target
#[derive(Component)]
pub struct ChildOf(Entity);                    // Relationship 组件

// target 实体上：反射所有指向它的 source 列表
#[derive(Component)]
pub struct Children(Vec<Entity>);              // RelationshipTarget 组件
```

- **无独立索引结构**（源码 grep `sparse` 零匹配——修正了"用 ComponentSparseSet"的猜测）
- 一致性完全靠**组件 hooks**：
  - `ChildOf::on_insert`：插入时给 target 自动插/追加 `Children`
  - `ChildOf::on_discard`：移除时从 target 集合删除 source，集空删 `Children`
  - `Children::on_discard`：target 组件被删时反向移除所有 source 的 `ChildOf`
  - hooks 在 `DeferredWorld` 内通过 commands 排队执行

### 1.2 不拆 archetype（non-fragmenting）

- target 编码在**组件值**（`ChildOf(Entity)`）而非 archetype 签名 → 改 target 只改值，**不触发 archetype 迁移**
- 官方源码未用 "fragmenting" 词（仅 bevy_121 README 使用）；此为机制推断

### 1.3 反向查询：RelationshipTarget 组件的集合字段

- `RelationshipSourceCollection` trait，官方 7 种实现：`Vec<Entity>` / `SmallVec` / `EntityHashSet` / `EntityIndexSet` / `BTreeSet` / `IndexSet` / 裸 `Entity`（1:1）
- API：`query.relationship_sources::<S>(entity)`（target → sources）、`query.related::<R>(entity)`（source → target）
- 遍历：`iter_ancestors` / `iter_descendants`（BFS）/ `iter_siblings` / `iter_leaves` / `root_ancestor`

### 1.4 级联删除：LINKED_SPAWN 标志 + hook

- `Children` 标 `linked_spawn` → `on_despawn` hook 遍历集合对每个 source `try_despawn()` → 递归级联
- 克隆联动：`linked_cloning` 时克隆父递归克隆子

### 1.5 多实例限制

- **出边**：每个 source 每类关系最多 1 条（`ChildOf` 只能有一个 target）
- **入边**：target 可收集多 source（1:N），集合禁重复
- **M:N 不支持**（bevy_121 README 明确）
- 1:1 变体：集合用裸 `Entity`，新插入先移除旧 source（`source_to_remove_before_add`）

### 1.6 Hierarchy 已迁移到 Relations

- 旧 `Parent` 组件被 `ChildOf` 取代；`add_child`/`with_children` 保留为关系新实现
- `Children(Vec<Entity>)` 带 `linked_spawn` 标志

### 1.7 与 EntJoy 对比

| 维度 | Bevy 0.16 | EntJoy（S23/S24） |
|------|-----------|-------------------|
| 存储 | 普通组件 `ChildOf(Entity)` + `Children(Vec)` | 组件列（`RelationSlot` 8B 值） |
| 拆 archetype | ❌（值存组件） | ❌（值存列） |
| 反向索引 | 组件 hooks 双向同步（`Children` 集合） | 主动 `RelationIndex`（target→HashSet） |
| 级联删除 | `linked_spawn` 标志 + `on_despawn` hook | `DestroyEntityCascade` 递归 |
| 1 实体多同类型关系 | ❌（出边限 1） | ❌（路径 A 单实例） |
| target→sources 查询 | `relationship_sources`（组件集合读） | `GetRelationsOf`（索引 O(1)） |
| 关系遍历 | `iter_descendants`/`iter_ancestors` 等 | 🔲 未实现（可借鉴） |

**EntJoy 差距**：缺 `iter_ancestors`/`iter_descendants`/`iter_siblings` 等**关系遍历 API**（Bevy 有，状态机/层级遍历会用到）。索引主动维护 vs hooks 双向同步——EntJoy 的 RelationIndex 是 O(1) 但需要显式维护；Bevy hooks 是组件生命周期自动，但 DeferredWorld 排队有延迟。

## 二、Flecs 关系（调研完成，基于 DeepWiki + flecs.c 源码）

### 2.1 存储：pair 编码进 64 位 id，作为 table 签名的"一等公民"

- **pair** = `ecs_id_t`（64 位）：bit63 `ECS_PAIR` 标志 + bits62-32 relationship 实体 ID + bits31-0 target 实体 ID（`ecs_pair(rel, tgt)`）
- **编码进 table type**：`(Rel, Target)` 与 `(Rel, Target2)` 是**不同 id、不同 type 项**，像组件一样存 archetype 表
- 每个 pair id 对应 `ecs_id_record_t`（组件记录），其 `ecs_table_cache_t` 索引所有含该 pair 的表

### 2.2 是否拆 archetype？默认拆，但有三种例外

| 模式 | 行为 |
|------|------|
| **默认** | `(ChildOf, ParentA)` 与 `(ChildOf, ParentB)` 不同 type → **不同表**，碎片化 |
| `EcsDontFragment` | pair 不进签名：存 `ecs_sparse_t`（稀疏集）或 ChildOf 场景存 `EcsParent{parent}` 组件 → 实体集中一张表 |
| `EcsUnion` | pair 不进 type，用行级 `ecs_switch_t`（switch 列），当前 target 存行值 |
| `EcsExclusive` | 每实体限 1 target，加新 target 时**原位替换**旧 pair |

### 2.3 反向查询：id_record 表缓存 + 通配符链表

- `ecs_id_record_t` 三个双向链表钩子：`first`（挂在 `(R,*)` 上）/ `second`（挂在 `(*,O)` 上）/ `trav`（可遍历关系）
- 反向查询 `(*, Target)` = 从 `(*, Target)` 记录的 `second` 链表枚举
- 行级标记：`ecs_record_t.row` flags 含 `EcsEntityIsTarget`（被用作 target）/ `EcsEntityIsId`（被用作关系类型）——删除实体时快速发现引用者

### 2.4 级联删除：声明式 cleanup 策略 + 递归标记

- `(ChildOf, OnDeleteTarget, EcsDelete)`：父删子自动删（声明式注册）
- `flecs_on_delete`：标记 id_record → 遍历含该 id 的所有表 → 递归 `flecs_targets_mark_for_delete`（检查每实体 row flags）→ 统一清理
- 递归本质：删 target → 其 row flag 有 `EcsEntityIsTarget` → 触发 `(*, entity)` 的 OnDeleteTarget=Delete → 删所有持有者 → 递归

### 2.5 多实例：天然支持

- 多个 `(Rel, Target1)`/`(Rel, Target2)` **自然共存**（每个 pair 独立 type 项、独立 id_record、独立数据列）
- `ecs_table_record_t.count` = 该 id 在表中出现次数（多实例时 >1）
- `EcsExclusive` 例外：ChildOf 等标记 exclusive 的关系每实体限 1 target

### 2.6 关系数据：pair 关联组件时存 SoA 列

- relationship 关联 `EcsComponent` → pair 实例数据存表中该 pair ID 对应列（`ecs_set_pair`/`ecs_get_pair`）
- 无数据的关系 = tag（不占列）

### 2.7 与 EntJoy 对比

| 维度 | Flecs | EntJoy |
|------|-------|--------|
| 存储 | pair 64 位 id 进 table 签名 | RelationSlot 8B 值进组件列 |
| 拆 archetype | 默认拆（DontFragment 可选） | ❌ 不拆 |
| 反向查询 | id_record 表缓存 + 通配符链表 | RelationIndex（HashSet） |
| 级联删除 | 声明式 OnDeleteTarget + 递归标记 | DestroyEntityCascade 递归 |
| 多实例 | ✅ 天然 | ❌ 路径 A 单实例 |
| 关系数据 | ✅ pair 列 | 🔲 RelationSlot 可扩展 |
| 遍历 | `(Rel,*)`/`(*,Target)` 通配符 + up/down 遍历 | 🔲 未实现 |

**Flecs 对 EntJoy 的启示**：
1. **EcsDontFragment/EcsUnion**：Flecs 也承认"关系默认拆表"有碎片化问题，用 trait 按需抑制——EntJoy 从一开始就不拆（更优）
2. **多实例**：Flecs 天然支持（pair 独立 type 项）；EntJoy 路径 B 预留，但 Flecs 证明多实例与"不拆 archetype"可共存（EcsUnion switch 列）
3. **声明式级联**：Flecs 用 `(ChildOf, OnDeleteTarget, EcsDelete)` 声明，EntJoy 用显式 `DestroyEntityCascade` API——Flecs 更"自动"，EntJoy 更"显式"

## 三、Unity DOTS 关系（LinkedEntityGroup）

来源：[Linked entity groups（Unity Entities 1.4 官方文档）](https://docs.unity3d.com/Packages/com.unity.entities@1.4/manual/linked-entity-group.html)、[LinkedEntityGroup API](https://docs.unity.cn/Packages/com.unity.entities%401.0/api/Unity.Entities.LinkedEntityGroup.html)

### 3.1 机制

- **`LinkedEntityGroup` 是 Buffer 组件**（`IBufferElementData`）：实体上挂一个动态数组，显式列出关联的实体（通常是根 + 所有子）
- 父子层级：**根实体持有 `LinkedEntityGroup` buffer，列出自身 + 所有后代**
- **级联删除**：`DestroyEntity(linkedGroupRoot)` 时，Unity 自动把 buffer 里所有实体一起销毁（这是 LinkedEntityGroup 的核心用途）
- **无反向索引**：target → sources 没有内建结构，需要自己遍历或维护
- **创建**：烘焙（Baking）时自动生成，或手动 `AddBuffer<LinkedEntityGroup>()`

### 3.2 特点

| 维度 | Unity LinkedEntityGroup |
|------|------------------------|
| 存储 | Buffer 组件（显式实体列表） |
| 拆 archetype | ❌（buffer 是普通组件） |
| 反向索引 | ❌ 无（需手动维护） |
| 级联删除 | ✅ 内建（DestroyEntity 自动销毁 buffer 内实体） |
| 1 实体多同类型关系 | ✅（buffer 可列任意多） |
| 关系遍历 | 手动遍历 buffer |

### 3.3 对比

Unity 方案**最朴素**：关系就是"一个实体上列一堆实体"，没有 target 概念、没有反向查询、没有 hooks。它的优势是简单 + 级联删除内建；劣势是**只支持层级（根→全部后代），不支持任意关系**（如"喜欢"、"属于"），改关系要重建 buffer，且无反向查询。

## 四、三框架 vs EntJoy 总对比

| 维度 | Bevy 0.16 | Flecs | Unity | **EntJoy** |
|------|-----------|-------|-------|-----------|
| 存储 | 组件对（`ChildOf`+`Children`） | pair 64 位 id 进 table 签名 | Buffer 组件 | 组件列（`RelationSlot` 8B 值） |
| 拆 archetype | ❌ | ⚠️ 默认拆（DontFragment/Union 可选抑制） | ❌ | ❌ |
| 反向索引 | 组件 hooks 同步 `Children` | id_record 表缓存 + 通配符链表 | 无 | 主动 `RelationIndex`（O(1)） |
| 级联删除 | `linked_spawn` + hook | 声明式 OnDeleteTarget + 递归标记 | DestroyEntity 自动 | `DestroyEntityCascade` 递归 |
| 多同类型关系 | ❌ 出边限 1 | ✅ 天然（pair 独立项） | ✅ | ❌（路径 A 单实例，B 预留） |
| 关系遍历 API | `iter_ancestors`/`iter_descendants` 等 | `(Rel,*)`/`(*,Target)` 通配符 + up/down | 手动 | 🔲 未实现 |
| 关系数据 | 组件值自带 | ✅ pair 列 | 无 | `RelationSlot` 固定 8B（可扩展） |

**EntJoy 最接近 Bevy 0.16**（值存组件列 + 不拆 archetype + 显式级联），差距主要在**关系遍历 API**（ancestors/descendants/siblings）——这是状态机/层级场景的直接需求。Flecs 则证明**多实例关系与"不拆 archetype"可以共存**（EcsUnion switch 列 / DontFragment），为 EntJoy 路径 B 提供参考实现。
