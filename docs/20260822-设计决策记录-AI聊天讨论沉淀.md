## 一、NativeTranspiler 后端选择策略（核心议题）

### 1.1 现状：per-job 手动选后端（无自动路由）
- **事实**：后端由 `[NativeTranspile(Target = Cpp | Ispc)]` 在**整个 Job 粒度**上手动指定（`AttributeHelper.GetBackendTarget`，默认 `Cpp`）。生成器内无任何计算密度评分 / 启发式（无 `CodeMetrics`/`ShouldUseIspc`）。
- **聊天结论**：曾讨论「用户只标 `[NativeTranspile]`，系统自动决定 C++/ISPC」与「C++ 主体 + ISPC 内循环」混合翻译——两者均**需新增代码分析**，工程量高、易错，结论为**暂缓/不自动**。
- **状态**：⏸ 现状即聊天最终建议的「默认 Cpp，热点手动标 Ispc」；自动路由与混合翻译列为未来方向（见 §1.4）。

### 1.2 为什么 ClosestPointJob 用 ISPC 更快、LightJob 反之（已验证的判断）
- 计算密度决定后端优劣：`ClosestPointJobPointer`（重计算、内层数百次距离度量 + 规约 + 连续内存访问）→ ISPC 全量向量化收益大；`MoveJobChunkCSharp` 类 LightJob（仅乘加、内存带宽主导）→ C++ 自动向量化（/O2 /arch:AVX2）已等效且无跨边界调用开销。
- **LightJob 上 ISPC 慢 0.2ms 的根因（gather 惩罚）**：ISPC `foreach` 中 varied 索引 → `vpgatherdd`（延迟 ~20 周期、吞吐低），而 C++ 标量循环用连续 `vmovups`。该分析成立；生成器**未**做「连续访问改 uniform 指针 + 显式连续加载」改写（复杂度/UB 风险，不值得）。
- **状态**：✅ 认知已固化，指导示例标注；❌ 不实现 gather 规避改写。

### 1.3 智能降级（Smart Downgrade）
- 聊天建议：评分判为内存受限（算术指令少 + 连续访问）时，即使标了 `Target=Ispc` 也回退 C++ 并出 Info 诊断。
- **状态**：🔜 未实现。实践中的替代：用户按 1.2 自行判断标注（示例均显式标注）。

### 1.4 未来方向（未排期）
1. **自动后端路由**：在 NativeTranspilerGenerator 生成前插入 CodeMetrics 分析（算术数 +1 / 数学函数 +3 / 分支 -2 / 嵌套 +2 / 迭代量），阈值判 Cpp/Ispc。
2. **循环级混合翻译**：外层控制流留 C++，内层纯算术循环提取为 ISPC `export` 函数（`extern` 调用，跨 TU 无法内联，需迭代量 > 256 才划算——golden rule：调用开销固定，内层必须够重）。
3. 两者均依赖对拍基准，实施顺序排在 SIMD 两活路径统一之后（见 `archive/simd/20260820-NativeTranspiler与SourceGenerator重构计划.md` 遗留交接项）。

## 二、ISPC 与 C++ 库互操作（已确认的边界）

- ISPC 只认识 C 运行时 / POD：不能 `#include` 含 STL/class 的 C++ 头；`NativeMath.h`/`NativeSIMD.h`（纯 `static inline` C 风格）可被 ISPC 直接包含——**当前生成器正是这样共享数学头**（EntityBatchData/ChunkJobData 为 POD，C#/C++ `Sequential` 对齐）。
- 需要复杂 C++ 库时：C 包装层 `extern "C"` 暴露纯函数，ISPC `extern void fn(...)` 引用；跨边界调用无法内联，只适合非热路径。
- **状态**：✅ 边界已确立，生成器遵守（ISPC 只 emit 纯 C 语法）。

## 三、IJobEntity / IJobChunk 调度

### 3.1 IJobEntity ≡ IJobChunk（适配器）
- 已实现：`IJobEntitySourceGenerator` 生成 `__EntJoy_IJobEntityAdapter_X : IJobChunk`，`job.Schedule(query)` → `ChunkJobExtensions` → `NativeEcsScheduler.ScheduleChunk`；Execute 体 Roslyn 内联（形参 → span[__idx]、字段 → `Job.<field>`、`this` → `Job`、void return → continue）。详见 `20260820-NativeTranspiler与SourceGenerator重构计划.md` §9。
- **状态**：✅。注意：`[NativeTranspile]` 的 IJobEntity 的 `.Schedule(query)` 扩展由 ECS SG 统一生成（托管 adapter 路径）；如需**原生 C++/ISPC 执行**，显式调用 `NativeTranspiler.Bindings.NativeExports.Schedule_<Job>(ref job, query, dep)`（2026-08-22 修复 BindingsGenerator 不再为 IJobEntity 生成重复扩展后，原生入口仅保留在 NativeExports）。

### 3.2 IJobChunkBatch —— 明确不做 ❌
- 聊天两轮评估 + Unity 实践（`IJobEntityBatch` 已废弃）结论一致：批处理 Execute 只省函数调用（<1%，且每 Chunk 几百实体时占比 ~0.01%），跨 Chunk SIMD 因内存不连续是"海市蜃楼"；正确抽象层次是 Tile（调度层）而非 Execute（用户层）。
- **状态**：❌ 不实现。已有"Tile 分组多个 Chunk"（调度层批处理）。

### 3.3 Tile 粒度自适应（按实体数切分）—— 已实现 ✅
- 聊天建议"按实体总数而非 Chunk 数切 Tile"：已在 `JobSystem_Tiles.cpp` 落地（"实体数衡 tile 用它切分，替代固定 chunk 数"，`entityBatches[i].entityCount / chunks[i].entityCount` 计权），commit `fe846b9`。
- **状态**：✅。

## 四、ECS 容器安全（NativeArray / ArchetypeChunk）

### 4.1 NativeArray 安全层（比聊天设想更完备）
- 现状：`NativeArray<T>` 内建 `AtomicSafetyHandle`（**每次索引进出 `CheckReadAndThrow/CheckWriteAndThrow`**，越界/句柄非法即抛）、`_isOwner` 所有权标志、`DisposeSentinel`（DEBUG 下 GC 终结器泄漏检测）。视图（`GetSubArray/Reinterpret/FromExternalPtr/GetComponentDataNativeArray`）`_isOwner=false`，`Dispose()` **静默跳过释放**（不会误释放 Chunk 内存）。
- 聊天建议"Release 下 Dispose 视图抛异常"：**未采用**——当前为安全静默（不释放、不崩溃）；"引入 `NativeArrayView<T>` 无 Dispose 类型"：**未实施**。
- **状态**：✅ 安全目标已由既有机制达成（防误释放）；“Dispose 视图抛异常 / NativeArrayView 分离类型”⏸ 可选增强。

### 4.2 GetComponentDataNativeArray —— 保留（决策：暂不移除）
- 聊天结论：应从 `ArchetypeChunk` 移除（所有权语义冲突，`Span<T>` 完全替代）。
- 现状（2026-08-22）：`ArchetypeChunk.GetComponentDataNativeArray<T>()` **仍在**（L35），样例（`MoveJobChunkIspc` 等）也在用。
- **状态**：⏸ 未执行移除。数据安全不受影响（见 4.1）；是否移除属 API 面决策，可与 4.3 一并评估。

### 4.3 IJobChunk.Execute 签名 —— ChunkEnabledMask 参数保留
- 聊天建议：`Execute(ArchetypeChunk chunk)` 去掉 `in ChunkEnabledMask`，改为按需 `GetEnabledMask<T>()`。
- 现状：`IJobChunk.Execute(ArchetypeChunk chunk, in ChunkEnabledMask enabledMask)` **签名未变**；但 `ArchetypeChunk` 已提供 `GetEnabledMask<T>/IsComponentEnabled/SetComponentEnabled`（按需能力已具备）。
- **状态**：⏸ 参数精简未做（属 breaking change，影响所有 IJobChunk + SG 适配器 + 生成代码，需统一版本发布）。

## 五、Chunk / Archetype 与内存布局

### 5.1 Chunk/Archetype 结构体化 —— 暂缓 ⏸
- 现状：`Chunk` 为 `sealed unsafe class : IDisposable`；`Archetype` 持 `List<Chunk> _chunkList` + `List<nint> _slabs`（64KB slab）；`GetChunks()` 每帧 `new List<Chunk>`（分配）。
- 聊天结论（成立）：把 **Chunk 元数据**连续化（`NativeList<Chunk>`，300×40B=12KB 进 L1）收益明确（消除对象头/GC 根扫描/双跳转）；**数据块不要合并**（64KB 独立 slab 是缓存友好与 O(1) 增删的正确模型，19.2MB 大块会缓存污染 + 碎片整理灾难）。
- **状态**：⏸ 未实施。方向=元数据 struct 连续化 + 保留独立 64KB slab；优先级低于 B.1/B.3（TempAllocator / AddEntity O(n)）。

### 5.2 ChunkMemoryPool —— 必需但未实现 🔜
- 聊天结论：64KB 固定块池化（无锁栈/Interlocked）防碎片、O(1) 分配，长期运行服务器**必须有**。
- 现状：`_slabs` 列表存在，未见 ChunkMemoryPool 池化实现。
- **状态**：🔜 未实现（与 5.1 联动）。

### 5.3 合并瘦 Chunk（碎片整理） —— 未实现 🔜
- 聊天给出触发策略（利用率 <30%、每帧限量 1-2 块、主线程 Job 完成期执行）+ 收益量级（300 瘦块→9 满块，内存 -97%、调度 -97%）。属 ECS 维护机制，当前无实体增删压力场景，未排期。
- **状态**：🔜 未实现。

## 八、与 Unity DOTS 对标（已内化的架构观）

- **框架留 C#，用户计算下沉 C++/ISPC**——Unity（Burst）同款路线。Archetype 匹配 / EnabledComponent 位操作 / Chunk 迭代**不迁 C++**（控制流密集 + 调用频率低 + P/Invoke 单次 10-50ns 抵消收益）；C# JIT 对分支/接口调用已接近 C++。
- 唯一值得"原生化"的 ECS 操作 = 用户 Execute 体（当前 NativeTranspiler 已做）与批量内存拷贝（memcpy 类，非热点不需）。
- **状态**：✅ 架构现状与之完全一致（ECS 框架全 C#，调度核心 C++，用户逻辑可 transpile）。

## 九、JobSystem 生产就绪审计结论（Jobsystem聊天分析 摘要）

- **结论：可投产**，且聊天列举的防护在 2026-08-22 仍全部成立并更强：
  - 死锁：依赖链 10ms 协助预算（C++）/ 周期协助（Managed，无墙钟超时）+ Complete 超时兜底 + Chase-Lev `PopBottom` SeqCst fence + claimers 退役 handshake。
  - ABA：Managed `Generation` 代际 + C++ 64 位单调序号。
  - 跨 DLL 堆损坏：`EntJoy_GetPersistentAllocRef/GetPersistentFreeRef` 导出共享同一回调槽。
  - 内存：HandleState/BatchStorage/ManagedCompletion 池化 + TLS；ISPC TaskGroup 析构回收。
- **3 处已被后续演进更新**（聊天基于旧快照）：
  1. Native 调度核心由「全局 MPMC 环」→ 默认 **Chase-Lev 工作窃取**（`ENTJOY_USE_WORKSTEALING` 默认开）。
  2. 生产建议"默认关 CPU 亲和"已被推翻：现**默认开启**（worker 绑 1+idx、主线程绑 0；Chase-Lev 与旧路径均生效；`ENTJOY_WORKER_AFFINITY=0` 关闭）。
  3. Managed 原「30s CompleteTimeout 抛异常」被**无墙钟周期协助**取代（`CompleteAssistInterval=8ms` 回访推进，合法长任务不误报）。

## Phase 1-3 实施记录（2026-08-24）

### 1. Chunk Struct 化（Phase 1.6）

| 决策 | 选择 | 原因 |
|------|------|------|
| Chunk 类型 | `struct` 而非 `class` | 消除对象头/GC 根/指针跳转 |
| 元数据存储 | `ChunkMetadata` 类（每 Archetype 共享） | 4 个 `int[]` 不能放进 blittable struct |
| Archetype._chunkList | 保留 `List<Chunk>` | .NET 8+ `ref T` return + `CollectionsMarshal.AsSpan` |
| GCHandle 路径 | `ChunkRef` 包装类 | GCHandle.Alloc 不能接受 struct |
| null 检查 | `MemoryBlock == nint.Zero` | struct 不能与 null 比较 |

**性能结果**：C# IJobChunk 0.638→0.396 ms（-38%），Sleep 路径 -9%。

### 2. ENTJOY_SAFETY 运行时开关

| 决策 | 选择 | 原因 |
|------|------|------|
| 安全检查方式 | 运行时 volatile bool 开关 | Release 下仍可检查，需要时可关闭 |
| 默认值 | `true`（开启） | 安全优先 |

### 3. Archetype Edges（Phase 2.1）

| 决策 | 选择 | 原因 |
|------|------|------|
| Edge 存储 | `_addEdges` / `_removeEdges` 字典 | O(1) 查找，避免重复 GetOrCreateArchetype |
| Edge miss 处理 | GetOrCreateArchetype + 写回 cache | 首次调用后缓存 |

### 4. Chunk lazy zero（Phase 2.3）

| 决策 | 选择 | 原因 |
|------|------|------|
| 整体清零 | 移除 `Unsafe.InitBlock` | `AddEntity` 已逐 slot 清零，未使用 slot 不会被访问 |
| 批量创建加速 | 1.26x → 1.79x | lazy zero 减少了 chunk 初始化开销 |

### 5. Selective Wait（Phase 3.2）

| 决策 | 选择 | 原因 |
|------|------|------|
| 跟踪粒度 | Per-Archetype（而非 Per-Chunk） | Archetype 是组件集合的身份边界 |
| 等待策略 | `CompleteArchetypeJobs(affectedArchetypes)` | 只等待受影响 Archetype 的 Job |
| NewEntity | 保持 `CompleteActiveJobs` | 需要知道目标 Archetype，但 GetOrCreateArchetype 需在锁内 |
| RefRO/RefRW | 移到 EntJoy.ECS，后续再设计 | 当前用 written component types 声明替代 |

### 6. Batch CreateEntities（Phase 3.4）

| 决策 | 选择 | 原因 |
