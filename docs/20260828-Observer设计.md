## 一、动机：为什么 WithChanged 不够

现有 `WithChanged<T>()`（2026-08-25 落地）是 **pull-based 变更过滤**：

```
Set<T>/SetRaw → NotifyComponentChanged → Chunk.MarkEntityChanged（每实体 1 bit）
查询时 → ChunkJobCollector.MatchChangedFilter → chunk.HasAnyEntityChanged()（chunk 级粗过滤）
帧末 → EntityManager.ClearAllChangedBitMasks() 清零
```

四个硬局限：

| # | 局限 | 根因 |
|---|------|------|
| 1 | **不覆盖 Add/Remove** | 结构变更走 Archetype 迁移，不经 Set/NotifyComponentChanged，位掩码不置位 |
| 2 | **chunk 级粒度** | `HasAnyEntityChanged` 只判断"chunk 内有没有任何实体变过"，过滤后仍需整 chunk 遍历 |
| 3 | **每帧轮询** | 用户必须每帧跑查询 + 检查，无"事件来了才醒" |
| 4 | **swap-pop 位掩码错位** | `RemoveEntity` 迁移时变更位不随实体移动（`20260825` §7.1 已记录） |

Observer 补 1/3 两点：**结构变更自动 push**，无需轮询。

### 与已有机制的关系（定位矩阵）

| 维度 | WithChanged（已有） | Event Channel S18（已有） | **Observer（本设计）** |
|---|---|---|---|
| 触发模式 | pull（查询时检查） | push（手动 SendEvent） | **push（框架自动捕获）** |
| 事件面 | 仅 Set（值改） | 用户自定义事件 | **Add / Remove / Set / Destroyed** |
| 事件产生者 | `Set<T>` 隐式 | 用户代码 | 结构变更路径 + ECB Playback |
| 消费方式 | `WithChanged<T>()` 查询过滤 | `NextFrameEvents()` + ReadBuffer | **注册回调，被动接收** |
| 数据载体 | Chunk 位掩码 | 双缓冲 EventStream | **ECB 命令载荷 + 主线程直发** |

**分工原则**：
- **Observer** = 结构变化（Add/Remove/Destroy）的自动通知 + 主线程 Set 的即时通知。
- **WithChanged** = "本帧哪些实体值变过"的批量轮询（渲染 dirty、增量处理），保留。
- **Event Channel** = 用户语义事件（碰撞、死亡信号），保留。

## 二、事件模型

### 2.1 事件面与定义

| 事件 | 定义 | 捕获点 | push 时机 |
|------|------|--------|-----------|
| **Added** | 实体获得某组件（含新实体带组件创建） | AddComponent / CreateEntities / ECB Playback | 主线程立即；ECB 延迟到 Playback |
| **Removed** | 实体失去某组件（含 DestroyEntity） | RemoveComponent / DestroyEntity / ECB Playback | 同上 |
| **Set** | 组件值被写入 | `Archetype.Set<T>/SetRaw`（仅主线程路径，见 §5） | 主线程立即 |
| **Destroyed** | 实体销毁（对实体拥有的每个已订阅组件触发 Removed） | DestroyEntity | 同上 |

### 2.2 事件载荷

```csharp
public readonly struct ComponentEvent<T> where T : unmanaged
{
    public readonly Entity Entity;
    public readonly T NewValue;      // Added / Set 有效
    public readonly T OldValue;      // Removed 有效（记录/迁移前快照）；Set 时可选（见 §5.4）
    public readonly ObserverEventFlags Flags; // Added | Removed | Set | Destroyed
}
```

### 2.3 粒度决策

| 触发粒度 | 说明 | 决策 |
|----------|------|------|
| **实体级** | 每实体一次回调 | ✅ 默认（Flecs 同款） |
| chunk 级批量 | 一次回调带范围（start/count） | 🔲 v2 扩展（批量操作热路径优化，见 §9） |

v1 只做实体级，正确性优先。

## 三、触发时机（定稿：双模式）

### 3.1 总览

```
┌─────────────────────────────────────────────────────────────────┐
│  主线程直接结构变更（AddComponent/RemoveComponent/DestroyEntity） │
│    └─ 立即捕获事件（实体 + 值快照） → 立即派发回调   ← 方案 A     │
├─────────────────────────────────────────────────────────────────┤
│  Job 内结构变更（worker 线程）                                   │
│    └─ 用户显式 DeferredCommandBuffer 记录命令                    │
│        └─ 记录命令时：同时快照事件载荷进命令（旧值此时可读）      │
│    └─ 帧末主线程 Playback（遍历命令）                            │
│        └─ 执行结构变更 + 用命令载荷派发回调        ← Flecs merge  │
├─────────────────────────────────────────────────────────────────┤
│  主线程手动 ECB / 未来自动 ECB                                   │
│    └─ 与 Job 内 ECB 同一条 Playback 链路 → 统一延迟派发          │
└─────────────────────────────────────────────────────────────────┘
```

**决策**：
- **主线程直接结构变更 → 立即回调**（方案 A，Flecs 式）：语义直观、零帧延迟。
- **一切经 ECB 的结构变更 → Playback 遍历命令时派发**（Flecs staging+merge 同款）：
  - Job 内、主线程手动 ECB、未来 Auto-Defer（S13）统一走这条链路，Observer 只需挂在 Playback 一处。

### 3.2 为什么"Job 内"必须走 ECB 派发而不是立即回调

Job 在 worker 线程执行，结构变更被框架禁止（`EntityManager.cs` L141-144 直接抛
`"Structural changes are not allowed while a scheduled job is executing"`），
回调又必须在主线程跑（Observer 是 C# 托管能力）。因此：

```
Job 内无法立即回调（线程安全 + 结构变更禁令）
  → 事件先"物化"进 ECB 命令（记录时快照，worker 安全）
  → 帧末 Playback（主线程）遍历命令时统一派发
```

与 Flecs 完全一致：worker 写 staging（`ecs_staging_begin`），`ecs_merge` 统一触发 deferred observer。
参考：[Flecs Multithreading and Staging](https://deepwiki.com/SanderMertens/flecs/5.3-enum-reflection#1)。

### 3.3 重入保护（回调内再结构变更）

```
派发回调期间（ThreadStatic int s_observerDepth > 0）：
  ├─ 主线程立即回调内 → 结构变更一律转 ECB（延迟到 Playback，禁止立即）
  └─ Playback 派发回调内 → 结构变更记录到"下一批"延迟队列，当前 Playback 结束后再处理
```

- 防止：立即回调 → 递归 → 栈溢出；以及 Playback 派发回调 → 又往同一 ECB 写 → 无限循环。
- v1 简化：回调内结构变更**全部延迟**，文档约定"回调内如需改结构，直接自己写 ECB"。
- 检测机制：`s_observerDepth`（ThreadStatic），>0 时结构变更 API 抛错提示走 ECB（对齐现有 Job 内禁令的报错风格）。

## 四、事件链路：ECB 命令扩展（Job 内事件的核心载体）

### 4.1 现状：ECB 命令是扁平字节流

`DeferredCommandBuffer`（`src/EntJoy.ECS/Chunk/DeferredCommandBuffer.cs`）现有 4 种命令，OpCode 前缀 + 载荷：

| OpCode | 命令 | Playback 动作 |
|--------|------|---------------|
| 1 | CreateEntity(types) | `entityManager.NewEntity(types)` |
| 2 | DestroyEntity(entity) | `entityManager.DestroyEntity(entity)` |
| 3 | AddComponent(entity, value) | `entityManager.AddComponentRaw(entity, type, value)` |
| 4 | RemoveComponent(entity) | `entityManager.RemoveComponentRaw(entity, type)` |

Playback 已走 EntityManager 主入口（L153/L160/L175/L189）——这正是 Observer 想挂的点。

### 4.2 扩展：命令内嵌事件载荷

```
命令记录时（worker / 主线程，实体仍在原 archetype —— 旧值可安全读取）：
  AddComponent  → 快照 新值（value 已在命令里）        → 事件 Added
  RemoveComponent → 快照 旧值（此时实体未迁移）         → 事件 Removed
  DestroyEntity  → 快照 该实体所有已订阅组件的值        → 事件 Removed（=Destroyed）
  CreateEntity  → 无实体可快照；Playback 时 NewEntity 返回实体 → 事件 Added（值取初始值）

Playback 遍历命令（主线程）：
  for each cmd:
    1. 执行结构变更（现有逻辑不变）
    2. 查 observer 注册表（§6.1）
       有订阅 → 用命令载荷派发回调（不重新读实体 —— 实体可能已被前序命令移动/销毁）
       无订阅 → 跳过，零开销
```

**关键**：**旧值必须在记录命令时快照，不能在 Playback 时读**——Playback 遍历到该命令时，
实体可能已被同批更早的命令移动（swap-pop）或销毁，读出来的旧值不可靠。

### 4.3 命令内存布局（草案）

```
OP_ADD_COMPONENT 扩展后：
  [OpCode=3][Entity][ComponentTypeId][compSize][newValue bytes][eventFlags]
  ↑ 原命令载荷不变，末尾追加 eventFlags（1 int）

OP_REMOVE_COMPONENT 扩展后：
  [OpCode=4][Entity][ComponentTypeId][compSize][oldValue bytes][eventFlags]
  ↑ 新增：compSize + oldValue 快照（原命令无值）

OP_DESTROY_ENTITY 扩展后：
  [OpCode=2][Entity][subEventCount][{ComponentTypeId}{compSize}{value bytes}...]
  ↑ 新增：已订阅组件值快照列表（只对已订阅类型快照，控制体积）
```

> 实现注：DestroyEntity 的逐组件值快照只对"该实体当前 archetype 中**有 Removed 订阅**的组件"执行，
> 无订阅则命令保持原样（零额外体积）。是否快照以**记录命令时的注册表状态**为准。

## 五、Set 事件：主线程 vs Job 内写入

### 5.1 现状事实（代码级核对）

| 写入路径 | 代码位置 | 能否在写入点 hook |
|----------|----------|-------------------|
| `Archetype.Set<T>/SetRaw` | 主线程 API | ✅ 已有 `NotifyComponentChanged`（`Archetype.cs` L369），加一行分发即可 |
| **Job 内直接写 chunk 内存** | `IJobChunk.Execute` 里 `GetNativeArray<T>()[i] = x` | ❌ **裸内存写，无任何 API 经过** |

**Job 内写入是裸内存写**：托管 worker 经 `ChunkJobCallbacks.CreateChunkRangeCallback` 直接调用户 Execute
（`ChunkJobCallbacks.cs` L44），用户拿 chunk 裸写 → 不经过 Set → **连现有 WithChanged 位掩码都不会置位**
（这是既有限制，非新引入）。

**而且 Set 没有 ECB 命令载体**（ECB 只有 Create/Destroy/Add/Remove 四类）——用户提出的"Job 经 ECB 回调"
链路天然不覆盖值变化。业界同此：Bevy 值变化靠 Change Detection 轮询（[bevy#15287](https://github.com/bevyengine/bevy/issues/15287#issue-2534497099)）；
EnTT 只有走 `registry.replace<T>/patch<T>` 才触发 `on_update` 信号，直接 `get<T>()` 写不触发（[EntT Signals](https://deepwiki.com/skypjack/entt/3.5-signals-and-component-lifecycle#1)）。

### 5.2 决策：v1 范围

| 场景 | v1 行为 |
|------|---------|
| 主线程 `Set<T>/SetRaw` | ✅ **立即回调**（挂 `NotifyComponentChanged`） |
| Job 内值变化（IJobEntity/IJobChunk/Native） | ❌ **v1 不支持**（无 ECB 载体 + 裸内存写） |
| Job 内需要立即通知 | `EventBus.SendEvent`（S18，Managed/Native/ISPC 三后端） |

### 5.3 决策：Job 内 Set 事件 —— 统一用 `query.Writes<T>()` 显式声明（v1.5）

> 记录不阻塞 v1，用户确认后立项。参考 Bevy Change Detection（轮询）+ Flecs OnSet（延迟 merge）的折中。

**机制：写列显式声明 → 调度器分配 changed 位图 → 执行后标记 → 帧末批量分发 Set 事件**

```
job.Schedule(query.Writes<Position>())     // 显式声明写列
  └─ 调度器对写列生成 changed 位图指针（复用 enableBitMaps 同构机制）
  └─ 执行时（托管 adapter / C++ adapter）对写列数组写完后 MarkEntityChanged(idx)
  └─ 帧末同步点：扫 changed 位图 → 批量触发 Observer Set 事件
```

**决策：IJobChunk / IJobEntity 一律显式 `query.Writes<T>()`**（不做"无修饰=ref"的隐式推断，见 §5.4 决策记录）。

### 5.4 `query.Writes<T>()` API（v1.5）

```csharp
// 统一 API：查询上显式声明写列（"这个查询会让哪些组件被 Job 写入"）
var query = world.Query<Position, Velocity>().Writes<Position>();
job.Schedule(query);

// 语义：声明了才有 Set 事件；不声明 = 零开销、无 Set 事件（不报错）
// 代价：每 chunk 每写列 1 bit/实体 的 changed 位图内存 + 标记开销（按需付费）
// 声明粒度：按查询（定稿）——简单直观，Job 与查询解耦
```

### 5.4.1 决策记录：为什么不做"无修饰参数 = ref"的隐式写列推断

**提案回顾**：让 ECSSourceGenerator 自动检测 IJobChunk 写入；IJobEntity 无 ref/in 修饰的参数视为 ref（写列）。

**否决理由（分路径核实）**：

| 路径 | 自动检测写入的可行性 | 结论 |
|------|---------------------|------|
| **托管 IJobEntity**（非 NativeTranspile） | 生成器 L94 对所有参数统一生成 `GetComponentDataSpan<T>()`（**无视 ref/in**，Span 天然可写）——"无修饰=写"只是把现状**显式化**，无行为风险，可实现 | ✅ 技术上可行，但与"统一显式声明"决策冲突 |
| **NativeTranspile IJobEntity** | validator 强制参数只能是 ref/in（`NativeTranspileValidator.cs` L182），**无修饰参数现在直接 NT013 编译报错** | ❌ "无修饰=ref"= **放宽 validator 语义**，行为变更，影响面大 |
| **IJobChunk 自动写者分析** | `CppJobGenerator.CollectChunkNativeArrayTypes`（L724-762）已做方法体级组件收集（**只收读列，不分读写**）；自动检测写入需 **AST def-use 写者分析**（数组经局部变量/中间引用/别名传递时准确判定写） | ❌ 高成本；**保守近似会产生假 Set 事件**（"可能写"全置位 → 未写组件也被标记 → 假事件），不可接受 |

**决策：统一显式声明 `query.Writes<T>()`**，理由：
1. **IJobEntity 隐式规则只在托管路径有意义**（Native 路径要放宽 validator），两条路径行为分裂，违反"统一语义"原则。
2. IJobChunk 自动写者分析成本高且有假事件风险，显式声明 1 行、精确、零歧义。
3. 显式声明与 Unity DOTS 的 `[WriteGroup]`/`WithWriteGroup` 心智一致，用户可预期。

**顺带修复既有盲区**：让 Job 调度也置位 → `WithChanged` 与 Observer Set 事件共享同一份位图，一次标记两个消费者。

### 5.5 主线程 Set 事件细节

- 捕获点：`NotifyComponentChanged`（`Archetype.cs` L369）追加 observer 分发。
- 载荷：`NewValue` = 写入值；`OldValue` **v1 不提供**（读旧值 = 额外 1 次内存读，热路径成本；需要"值从 A 变 B"→ 用户自己缓存，或 v2 加 `[ObserveWithOldValue]`）。
- 去重：同一实体同一组件**同一帧多次 Set** → 每次触发（简单、可预期）；批量合并留 v2。
- 协同：主线程 Set 先置位掩码（WithChanged 仍可用），再分发 Observer 事件。两条链路并行。

## 六、API 设计

### 6.1 注册位置：World（门面）→ EntityManager（注册表）

用户拍板：**在 World 上注册**。实现上注册表存 `EntityManager`（结构变更 hook 点在 EntityManager/Archetype 层，见 §7），World 提供门面 API：

```csharp
// World 门面（转发到 EntityManager._observerRegistry）
ObserverHandle world.AddObserver<TComponent>(
    ObserverEvents events,                       // Added | Removed | Set | Destroyed
    Action<ComponentEvent<TComponent>> callback) // 参数 struct 零装箱
    where TComponent : unmanaged;

void world.RemoveObserver<TComponent>(ObserverHandle handle);
void world.ClearObservers<TComponent>();         // World.Dispose 自动清理
```

- 回调统一在主线程执行（主线程立即派发 + Playback 主线程派发）→ **无跨线程回调**。
- 回调内访问 `World` / `EntityManager` 安全；结构变更自动延迟（§3.3）。

### 6.2 事件位

```csharp
[Flags]
public enum ObserverEvents
{
    Added     = 1 << 0,
    Removed   = 1 << 1,
    Set       = 1 << 2,
    Destroyed = 1 << 3,   // 语义 = "DestroyEntity 时对本组件触发 Removed"
}
```

### 6.3 多组件观察

v1 只做单组件注册（`AddObserver<T>`）。跨组件组合（"同时拥有 A 和 B 时才回调"）需要状态跟踪，列 v2。

## 七、内部实现

### 7.1 注册表

```
EntityManager
  └─ _observers: Dictionary<ComponentTypeId, ObserverRegistry>
       └─ ObserverRegistry
            ├─ Added    : List<ObserverEntry<T>>   （静态类型 T，struct 回调盒）
            ├─ Removed  : List<ObserverEntry<T>>
            ├─ Set      : List<ObserverEntry<T>>
            └─ Destroyed: List<ObserverEntry<T>>   （= Removed 的实体级重映射）
```

- **零订阅者 fast path**：`EntityManager` 持 `int _observerCount` 全局计数，为 0 时结构变更路径**零额外分支**（一次 int 判断）。
- 回调类型化存储：每个注册生成一个 `IComponentObserver` 盒（per 组件类型 per 事件位），dispatch 时按 `ComponentTypeId` 查表，避免反射/装箱。
- NativeTranspile 边界：observer 是纯 C# 主线程能力，**不参与 native 化**。

### 7.2 挂钩点清单（single funnel）

| 入口 | 事件 | 捕获/派发 |
|------|------|-----------|
| `AddComponent<T>/AddComponentRaw`（主线程） | Added | 立即：实体 + 新值 |
| `RemoveComponent<T>/RemoveComponentRaw`（主线程） | Removed | 立即：实体 + 旧值（迁移前快照） |
| `DestroyEntity`（主线程） | Removed(=Destroyed) | 立即：对每个已订阅组件快照 |
| `CreateEntity(s)`（主线程，带组件） | Added | 立即 |
| `Set<T>/SetRaw`（主线程） | Set | 立即（§5.5） |
| **`DeferredCommandBuffer.Playback`（遍历命令）** | 全部 | 延迟：用命令载荷派发（§4） |

**要求**：所有结构变更（含 future 新增路径）必须经由这些入口或 ECB Playback，禁止绕过。

### 7.3 主线程立即派发（以 RemoveComponent 为例）

```
RemoveComponent(entity, T)
  1. 解析位置（archetype + chunk + slot）
  2. 若该组件类型有 Removed 订阅者：
     a. 快照旧值（CopyBlock 出栈）
     b. CompleteArchetypeJobs（结构变更前等待，现有流程）
     c. 迁移实体到目标 archetype
     d. 派发 Removed 回调（entity, oldValue）—— 迁移完成后派发，回调内可安全查询实体
  3. 若无订阅者：走现有路径，零额外开销
```

### 7.4 Playback 派发（Job 内事件）

```
DeferredCommandBuffer.Playback(entityManager)
  ── 现有：逐命令执行结构变更
  ── 新增：每条命令执行后，若命令带 eventFlags 且注册表有订阅者：
       用命令载荷（实体 + 新旧值快照）派发回调
  ── 派发期间 s_observerDepth++（防 §3.3 重入）
```

## 八、边界与坑

| # | 坑 | 处理 |
|---|----|------|
| 1 | **swap-pop 实体移动** | 事件在迁移前捕获实体 + 新旧值快照（主线程 §7.3 / ECB §4.2 均已覆盖）；不得在迁移后读 slot |
| 2 | **ECB 旧值快照时机** | 必须**记录命令时**快照；Playback 时实体可能已被前序命令移动/销毁 |
| 3 | **回调内结构变更（reentrancy）** | `s_observerDepth` 检测 → 全部转延迟（§3.3） |
| 4 | 回调内查询同一实体 | 迁移完成后才派发（§7.3 顺序保证） |
| 5 | 回调抛异常 | 捕获 + 记录（对齐 `NativeJobCore.RecordJobException` 风格），不中断剩余回调；文档约定回调不得抛 |
| 6 | `DestroyEntity` 多组件 Removed 顺序 | 按组件在 archetype 中的存储顺序（确定性） |
| 7 | 订阅者回调里 Unsubscribe/AddObserver | 分发时对订阅列表做快照（先拷贝再遍历） |
| 8 | 世界销毁 | World.Dispose 清空全部 observer 注册表 |
| 9 | `Set` 相同值 | v1 不做值比较（写入即事件）；需要"值真的变了"→ v2 `EqualValueFilter` |
| 10 | Job 内值变化 Set 事件 | v1 不支持（§5.2），v1.5 changed 位图候选（§5.3） |
| 11 | **同批 ECB 多条命令同一实体**（如 Add 后 Remove） | 按 Playback 顺序派发（Add→Removed 依次），事件顺序与命令顺序一致，文档约定 |
| 12 | Playback 派发回调内再写 ECB | 写"下一批"延迟队列，当前 Playback 结束后再处理（§3.3） |

## 九、测试计划

```
1. 主线程立即回调：
   - AddComponent<Health> → Added(1)，回调内实体可查 ✅
   - Set → Set(1)，NewValue 正确 ✅
   - RemoveComponent → Removed(1)，OldValue 正确（迁移前快照）✅
2. 销毁：DestroyEntity → 对 Health 触发 Removed（实体在回调内仍可读）✅
3. 新实体带组件：CreateEntity(Position) → Added(1) ✅
4. Job 内 ECB：
   - Job 内 ecb.AddComponent(e, h) → Playback 后 Added(1) ✅
   - Job 内 ecb.RemoveComponent<Health>(e) → Playback 后 Removed(1)，OldValue 为记录时快照 ✅
   - Job 内 ecb.DestroyEntity(e) → Playback 后对已订阅组件触发 Removed ✅
5. ECB 旧值快照正确性：
   - 同一 ECB 先 AddComponent 再 RemoveComponent 同一实体 → 两次事件，Removed.OldValue = 刚 Add 的值 ✅
   - 先 DestroyEntity 再操作同实体 → 事件不崩、Removed 载荷为销毁前快照 ✅
6. reentrancy：主线程回调内 AddComponent(其他组件) → 延迟到 Playback，无递归 ✅
7. 零订阅者：无 observer 时结构变更路径开销 ≈ 基线（benchmark 断言）✅
8. 回调内 Unsubscribe → 不抛异常、后续不再回调 ✅
9. 批量：CreateEntities(10000) + Added 订阅 → 10000 次事件（顺序正确）✅
10. 多 World：world1/world2 各自 observer 隔离 ✅
11. 回调抛异常 → 记录不中断 ✅
12. 主线程手动 ECB（不经 Job）→ 同样走 Playback 派发 ✅
```

### 性能验收

- 无订阅者：结构变更路径 0 额外分支成本（微基准对比基线）。
- 单订阅者：主线程 AddComponent 额外开销 < 100ns（快照 + dispatch）。
- Job 内 ECB 带事件 vs 不带：命令体积增量（快照区）与派发开销可测量，10 万实体 < 基线 × 1.3。
- 无 Removed 订阅时 DestroyEntity 命令不膨胀（只快照有订阅的组件）。
