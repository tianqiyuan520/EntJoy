## 二、S26：Component 存取生成（方案 A，已定）

### 2.1 API 形态

用户写：

```csharp
[ECSComponent]
public partial struct Position
{
    public float X, Y;
}
```

生成器输出（编译进用户程序集）：

```csharp
// <auto-generated/>
public partial struct Position : global::EntJoy.ECS.IComponentData { }
```

用户**不写** `: IComponentData`，但所有要求该接口约束的 API 直接可用。

### 2.2 为什么是方案 A（特性标记）而非 B（完全隐式）

| 维度 | A：`[ECSComponent] partial struct` | B：完全隐式（去接口约束） |
|---|---|---|
| 类型安全 | 显式标记，普通 struct 不会静默变组件 | 任何 blittable struct 都是组件，误用静默化 |
| 改动面 | 1 特性 + 1 生成器，核心零改动 | 放开 `Set<T>`/`GetComponent<T>`/`DCB.AddComponent<T>` 全部约束 |
| 符合定位 | §22.6「不替用户做决定」 | 违背（隐式替用户决定） |

### 2.3 现状核对（实现依据）

| 事实 | 位置 |
|---|---|
| 组件**注册已自动化**（懒注册，首次使用即注册），无需生成注册代码 | `ComponentTypeManager.cs:29-78` |
| `IComponentData` 是唯一约束点：`Set<T>`/`GetComponent<T>`/`DCB.AddComponent<T>` | `EntityManager.cs:1078/1140`、`DeferredCommandBuffer.cs:98` |
| `AddComponent<T>`/`RemoveComponent<T>` 已是 `where T : struct`，不受影响 | `EntityManager.cs:878/887` |
| `Query<T>` 已是 `where T : struct`，补接口后语义更一致 | `World.cs:117` |
| 生成器已在测试工程挂载（`EntJoy.ECS.Tests.csproj:15`），但 **EntJoy.ECS.csproj 未挂**（本次补上） | — |

### 2.4 特性定义

`src/EntJoy.ECS/Component/ECSComponentAttribute.cs`：

```csharp
[AttributeUsage(AttributeTargets.Struct, AllowMultiple = false, Inherited = false)]
public sealed class ECSComponentAttribute : Attribute { }
```

### 2.5 生成器规则与诊断

扫描 `StructDeclarationSyntax` 带 `[ECSComponent]`，语义确认特性符号是 `EntJoy.ECS.ECSComponentAttribute`
（防同名特性误判）。按序判定：

| 判定 | 结果 |
|---|---|
| 已实现任一 ECS 组件接口（IComponentData/ISharedComponentData/IRelationComponent/IEnableableComponent） | **跳过**（幂等，不重复补接口，不报错） |
| 泛型 struct（TypeParameters.Length > 0） | 诊断 **EJ2003**（组件不能是开放泛型） |
| 非 `partial` | 诊断 **EJ2001**（提示加 partial，不输出补丁避免 CS0260 噪声） |
| 含托管引用字段（非 blittable） | 诊断 **EJ2002**（报出违规字段路径） |
| 通过 | 输出 `partial struct X : IComponentData` |

**blittable 递归判定**：`IPointerTypeSymbol`→true；原生 `SpecialType`→true（String/Object 除外→false）；
enum→true；struct→递归检查实例字段（`ISet<string>` 防环）；class/interface/delegate/array/dynamic→false。

**输出细节**：accessibility 取原声明（public/internal）；namespace 与原声明一致（global namespace 不输出块）；
接口用 `global::EntJoy.ECS.IComponentData` 全限定；文件名 `{TypeName}_ECSComponent.g.cs`。

### 2.6 挂载

`EntJoy.ECS.csproj` 增加：

```xml
<ProjectReference Include="..\EntJoy.ECS.SourceGenerator\EntJoy.ECS.SourceGenerator.csproj"
                  OutputItemType="Analyzer" ReferenceOutputAssembly="false" />
```

使引用 EntJoy.ECS 的用户自动获得生成器（EntJoy.ECS 自身无 `[ECSComponent]` 类型，编译无副作用）。

### 2.7 验收标准（验证先行）

1. **编译期**：生成器单测通过——无 `IComponentData` 标记的 `[ECSComponent] partial struct` 组件可编译，
   且能通过 `Set`/`GetComponent`/`DCB.AddComponent` 的 `IComponentData` 约束。
2. **运行期**：集成测试覆盖 `Set`/`GetComponent`/`Query` 遍历/`AddComponent`/`RemoveComponent`/`DCB.AddComponent` 全链路。
3. **诊断**：非 partial / 泛型 / 含托管字段三类各触发对应 EJ2001/EJ2003/EJ2002（编译期验证，随测试工程编译触发）。
4. **回归**：全量测试（基线 108/108）不回归，无新增构建警告。

## 三、S27：System 注册生成（方案 A，已实现）

**消灭样板**：逐个手写 `runner.RegisterSystem<T>()`（样板 + 漏注册风险）。

**方案 A（已落地）**：生成器扫描同程序集所有 `struct : ISystem`，生成 `SystemRegistry.RegisterAll(SystemRunner)`，
一行注册全部。依赖声明（[Read]/[Write]）保持现状，由 ScheduleGraph 反射读取。

**设计要点**：
- 语义验证实现 `EntJoy.ECS.ISystem`（防同名接口误判），收集 `global::` 全限定类型名。
- 生成 `public static class SystemRegistry { public static void RegisterAll(SystemRunner runner) { ... } }`，
  方法体内为每个 System 输出 `runner.RegisterSystem<global::Full.Name>();`，按类型全名排序（确定性输出），置于 global namespace。
- **opt-out（对齐 Unity DOTS `[DisableAutoCreation]`）**：带 `[DisableAutoCreation]` 的 System 被生成器跳过，
  不加入 `RegisterAll`，需手动 `RegisterSystem<T>()`（如特殊初始化顺序、条件注册场景）。
- 限制：源生成器只能收集当前编译单元（用户程序集）；库内 System 不在收集范围（本就由库自管）。

**依赖修正**：文档标注 S27 依赖「S9」已砍（S9 SystemGraph 合并进 S7-new），实际依赖 Schedule Graph + SystemRunner，**均已就绪**。

**验收**：`SystemRegistrationGeneratorTests`（`RegisterAll_RegistersAndRunsAllSystems` + `RegisterAll_SkipsDisableAutoCreationSystems`，全量 114 通过）。

## 四、S32：Reactive System 生成（已实现）

**消灭样板**：手写 `world.AddObserver<T>(events, callback)` 订阅组件生命周期事件。

**底层已就绪**：Observer（S8-new，push 回调 + 批量 span 合并）；回调签名
`ObserverCallback<TComponent>(ReadOnlySpan<Entity>, ReadOnlySpan<TComponent>)`，事件位 `ObserverEvents`
（Added/Removed/Set/Destroyed，`[Flags]`）。

**API 形态（方案 A，已落地）**：

```csharp
[Reactive(ObserverEvents.Added | ObserverEvents.Set)]   // 事件从特性来，可叠加多个
public struct HealthReactiveHandler
{
    // 组件类型从第二个 span 参数推导；Execute 必须 static
    public static void Execute(in ReadOnlySpan<Entity> entities, in ReadOnlySpan<Health> values) { ... }
}
```

**生成器规则**：
- 语义验证 `[Reactive]` 特性为 `EntJoy.ECS.ReactiveAttribute`（防同名误判）。
- Execute 验证：存在且 static、签名 `(in ReadOnlySpan&lt;Entity&gt;, in ReadOnlySpan&lt;T&gt;)` → void；违规报 EJ2011（缺 Execute）/ EJ2012（签名错）。
- 特性参数 `ObserverEvents` 枚举常量 → 事件位 int → `ObserverEvents.X | ObserverEvents.Y` 表达式（支持组合）。
- 生成 `ReactiveSystemRegistry.RegisterAll(World)`（global namespace，按处理器全名排序），每个注册项输出
  `world.AddObserver<T>(events, (entities, values) => Handler.Execute(entities, values));`。

**验收**：`ReactiveSystemGeneratorTests` 2 个测试（Added+Set 派发 + 值传递、Set+Removed 派发，全量 116 通过）；
`ReactiveDemo` 运行 OK（Calls=2、LastValue=88、Removed=1）。

## 六、风险与缓解

| 风险 | 缓解 |
|---|---|
| blittable 递归检查误报（嵌套 struct 含内建 struct 字段） | 递归检查 + SpecialType/enum/指针白名单；诊断带字段路径便于定位 |
| 生成器增量缓存失效 | 复用现有生成器缓存模式 |

| 用户既写特性又手写接口 | 已实现接口则跳过（幂等），不报错 |
