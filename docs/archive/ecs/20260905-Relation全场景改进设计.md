> **范围**：在现有关系系统（S23/S24/Q1/Q2，`RelationSlot` 8B 单值列 + `RelationIndex` 反向 + 遍历 API + 级联）基础上，参考 Flecs 关系机制，补齐"关系数据 / 独占 1:1 / 出边多值 1:N / M:N / 声明式级联"能力，覆盖各种业务场景。

>
> **⚠️ 跨分析器可见性约束（实测发现）**：源生成器（EntJoy.ECS.SourceGenerator）注入的 `Slot1..N-1` 字段对 NativeTranspiler 分析器**不可见**（独立分析器语义模型不合并对方输出）→ NativeTranspiler 收集该类型时字段不完整 → Bindings 不生成 → 级联 CS0234 编译失败。**进 Job 的定长多槽列类型必须手写全部槽位字段**（`Target` + `Slot1..N-1` 显式声明；源生成器检测到已含 `Slot1` 时幂等跳过）。纯主线程使用的定长类型可依赖源生成器注入。

## 二、设计原则（参考 Flecs，与现有决策的关系）

### 2.1 参考 Flecs 的机制

Flecs 关系核心 = **pair 一等公民**：`(Rel, Target)` 编码进 64 位 id，作为独立 type 项进 table 签名，多实例天然共存；pair 可关联组件（关系数据）；`EcsExclusive` 声明独占；`OnDeleteTarget` 声明式级联；`EcsUnion` 用行级 switch 列抑制拆表。

### 2.2 明确边界（两个关键澄清）

1. **不照搬 pair 进签名**：Flecs 默认拆表（`(ChildOf, A)` 与 `(ChildOf, B)` 不同表），EntJoy 自 S23 起承诺"不拆 archetype"（`RelationSoA设计.md:14`）。改进沿用 `EcsUnion` 思想——**关系不进签名，多值走行级存储**，保持零拆表。
2. **澄清已废弃文档**：`RelationMulti-多实例关系设计.md:3` 废弃的是 **1:1 的 chunk 聚类存储**（高基数 target 稀疏爆炸）与 v1 外置表。本文 **不复活聚类**，1:1 维持现有列存储；多值关系用**托管列表 + 反向索引**（该文档 §2.2 明确写"查询数学最优"），与其废弃结论不冲突。

### 2.3 统一抽象

关系形态由**关系类型自身特性**决定，`AddRelationship` 单点路由：

```
IRelationComponent
 ├─ 默认（无特性）           → 单值列（现状，1 target/source，入边可多源）     = 多对一
 ├─ [ExclusiveRelation]      → 单值列 + target 侧唯一约束                    = 真 1:1
 ├─ [MultiRelation]          → 托管列表（正向）+ 反向索引（双向多值）          = 出边 1:N / M:N
 ├─ [MultiRelation] + [ExclusiveTarget] → 出边多值 + 入边唯一                = 一对多（背包）
 └─ TRel 带额外字段（任意）   → 列宽 = 真实 SizeOf，槽位偏移 = Target 字段偏移  = 关系数据
```

> **M:N 无需新存储**：`[MultiRelation]` 的正向 `List` + 反向 `HashSet` 在存储层天然双向多值，M:N 是其默认形态；`[ExclusiveTarget]` 只是在其上叠加"入边唯一"约束（见 §5.7）。

### 2.4 场景形态矩阵（适配验证）

关系能力 = 两个正交自由度（**出边**：单值/多值 × **入边**：单值/多值）。四种组合即覆盖全部业务场景：

| 场景示例 | 出边 | 入边 | 形态 | 特性组合 |
|----------|------|------|------|----------|
| 父子层级、阵营归属 | 单值 | 多值 | 多对一 | 默认（现状 ✅） |
| 索敌/仇恨（单目标） | 单值 | 多值 | 多对一 | 默认（现状 ✅） |
| 格子被谁占用、装备唯一持有 | 单值 | 单值 | 真 1:1 | `[ExclusiveRelation]`（Phase 2） |
| 背包/持有（角色多物品，物品唯一持有者） | **多值** | **单值** | 一对多 | `[MultiRelation]` + `[ExclusiveTarget]`（Phase 3） |
| 技能-角色、多标签 | 多值 | 多值 | M:N | `[MultiRelation]`（Phase 3） |
| 仇恨列表、图关系 | 多值 | 多值 | M:N | `[MultiRelation]`（Phase 3） |

## 三、Phase 1：关系数据（修复 P1）

### 3.1 问题确认（代码证据）

| 位置 | 行为 |
|------|------|
| `ComponentTypeManager.ComputeComponentSize`（:127-132） | `IRelationComponent` → 强制返回 `sizeof(RelationSlot)` = 8B |
| `ChunkMetadata.Create`（:104-113） | 列宽 = `componentTypes[i].Size`（= 8B） |
| `ComponentLookup._stride`（:31）、`EntityQuery`（:272） | Job/Span 步长 = `Unsafe.SizeOf<TRel>()` |
| Q2 修复（`RelationSoA设计.md:338-345`） | 要求 `TRel` 恰好 8B（含 `RelationSlot Target` 字段），`SizeOf` 才与列宽一致 |

→ 结论：**`TRel` 只要带一个额外字段（如 `int Count`），`SizeOf` = 16B ≠ 8B 列宽，Job 读取错位。文档 §13.2"天然支持"的断言不成立。**

### 3.2 设计

**约束**：关系类型第一个字段必须是 `RelationSlot Target`（`LayoutKind.Sequential` 保证偏移 0；可选 `Unsafe.OffsetOf` 防御校验）。

**改动点**：

| # | 位置 | 改动 |
|---|------|------|
| 1 | `ComponentTypeManager.ComputeComponentSize` | 关系类型列宽 = `Marshal.SizeOf(type)`（真实大小），不再强制 8B；注册时校验"首个字段为 `RelationSlot`"（`Unsafe.OffsetOf<TRel>("Target") == 0`），否则抛异常 |
| 2 | `ComponentType` 或 `ComponentTypeManager` | 新增元数据：`RelationSlotOffset`（Target 字段偏移，8B 类型 = 0） |
| 3 | `EntityManager.Relation.cs` 全部 `GetComponent<RelationSlot>` 读列 | 改为经 `RelationSlotOffset` 定位：`(RelationSlot*)(colBase + idx * stride + slotOffset)`。涉及：Add 覆盖读旧值（:68）、Remove 读旧值（:123）、GetRelationship（:149）、HasRelationship（:177）、TryGetRelationshipTarget（:264）、StillPointsTo（:447）、CleanupSourceRelations（:473） |
| 4 | `QueryEnumerable` 关系过滤（:139-148） | `_relBase` 同样经 `RelationSlotOffset` 定位（`RelationSlot*` 改为逐槽 `(byte*)base + slot * stride + slotOffset` 比较） |
| 5 | Observer 快照/派发（Add/Set/Destroyed） | 已按 `t.Size` 走列，自动适配新列宽，无需改动（验证即可） |
| 6 | NativeTranspiler | `TRel` 现含 `RelationSlot` 字段 + 额外字段，C++/ISPC 生成已支持嵌套字段（Q2 修复过 include 递归）；新增"字段偏移一致"的跨语言布局测试 |

### 3.3 兼容性

- 现有 `ChildOf`（仅 `RelationSlot Target`）→ `SizeOf` == 8B == 列宽，**行为与性能完全不变**（`slotOffset = 0`）。
- 带数据关系为纯增量能力。

### 3.4 验收

| # | 项 | 方法 |
|---|----|------|
| 1 | 带数据关系读写 | `struct Owns : IRelationComponent { RelationSlot Target; int Count; }`，Add 后 `GetRelationship<Owns>` 返回 target，列内 `Count` 可读写 |
| 2 | Job 步长一致 | IJobEntity 读 `in Owns`，10000 实体 sum(Count) == expected（防错位） |
| 3 | 兼容回归 | 现有 RelationTests / CascadeTests / RelationQueryTests 全量通过 |
| 4 | NativeTranspiler | C++/ISPC IJobChunk/IJobEntity 读带数据关系，六路径 sum 校验 |

## 四、Phase 2：独占 1:1（修复 P2）

### 4.1 设计

新增 `[ExclusiveRelation]` 特性（`AttributeTargets.Struct`）。`AddRelationship<TRel>` 路由：

- `[ExclusiveRelation]`：写入前查反向索引——target 当前已有同类型 source（`_relationIndex.TryGetSources`），有则先移除旧 source 的关系（`RemoveRelationship<TRel>(oldSource)`，含索引维护），再写新值 = **Flecs `EcsExclusive` 原位替换语义**。
- 默认：保持现状（多 source 可指向同一 target）。

API 面不变（`AddRelationship` 内部路由），仅新增特性 + 路由分支（`EntityManager.Relation.cs:63-90` 覆盖路径前插入独占检查）。

### 4.2 验收

| # | 项 | 方法 |
|---|----|------|
| 1 | 独占语义 | `[ExclusiveRelation] struct OccupiedBy`，A→T 后 B→T：A 的关系被移除，`GetRelationsOf<OccupiedBy>(T)` 仅 [B] |
| 2 | 索引一致性 | 独占替换后 `_relationIndex` 无旧 source 残留（`GetSourceCount(T) == 1`） |
| 3 | 兼容回归 | 现有关系测试全量通过（默认行为不变） |

## 五、Phase 3：出边多值 1:N / M:N（修复 P3）

### 5.1 存储设计

新增 `[MultiRelation]` 特性（`AttributeTargets.Struct`）。多值关系类型**不占 chunk 列**（避免 8B 单值列语义混淆），走新托管存储：

```csharp
/// <summary>多实例关系正向存储：relTypeId → sourceId → targets（有序列表，幂等去重）。</summary>
internal sealed class RelationListStore
{
    // 正向：source → targets（追加式 List<RelationSlot>，连续遍历）
    private readonly Dictionary<int, Dictionary<int, List<RelationSlot>>> _forward;
    // 反向：复用 EntityManager._relationIndex（target → (relType → sources)，已有）
}
```

- 正向：主线程托管（同 managed shared 纪律）；反向：复用 `RelationIndex`（O(1) 数学最优）。
- `[MultiRelation]` 与 `[ExclusiveRelation]` 互斥（校验特性冲突）；`[MultiRelation]` 可与 `[ExclusiveTarget]` 叠加。

### 5.2 API（`EntityManager.Relation.cs` + `World.Relation.cs` 转发）

```csharp
// [MultiRelation] 类型多值语义（1:1 列路径签名不变）
public void AddRelationship<TRel>(Entity entity, Entity target);           // 追加（幂等去重）
public void RemoveRelationship<TRel>(Entity entity, Entity target);        // 移除指定 target
public bool HasRelationship<TRel>(Entity entity, Entity target);           // 是否指向该 target
public Entity[] GetRelationships<TRel>(Entity entity);                     // 全部 targets
public int GetRelationshipCount<TRel>(Entity entity);
public void ClearRelationships<TRel>(Entity entity);                       // 实体销毁时自动调用
```

`AddRelationship<TRel>(entity, target)` 单点路由（`RelationListStore` vs 单值列），基于 `ComponentTypeManager` 新增元数据 `IsMultiRelation`。

### 5.7 入边唯一约束 `[ExclusiveTarget]`（背包场景）

背包 = 角色出边多值（多个物品）且物品入边唯一（一个物品至多一个持有者）。`[MultiRelation]` 已给出边多值，入边唯一需新增可叠加特性：

```csharp
[AttributeUsage(AttributeTargets.Struct)]
public sealed class ExclusiveTargetAttribute : Attribute { }

[MultiRelation]
[ExclusiveTarget]
public struct Owns : IRelationComponent { public RelationSlot Target; }   // 背包：角色→多物品，物品唯一持有者
```

**行为**：`AddRelationship<TRel>(entity, target)` 在追加前查反向索引——target 当前已有同类型 source（`_relationIndex.TryGetSources`），有则先移除旧 source 的该 target 条目（`RemoveRelationship<TRel>(oldSource, target)`），再追加。与 Phase 2 的 `[ExclusiveRelation]` 区别：

| 特性 | 出边 | 入边 | 场景 |
|------|------|------|------|
| `[ExclusiveRelation]` | 单值 | 唯一 | 格子占用、装备唯一持有 |
| `[MultiRelation]` | 多值 | 可多源 | 技能-角色、多标签 |
| `[MultiRelation] + [ExclusiveTarget]` | 多值 | 唯一 | 背包、组队名额 |

**验证**：重复 Add 同一物品到另一角色 → 旧角色该条目被移除，`GetRelationsOf<Owns>(item)` 恒为 1 个 source。

### 5.3 查询（按模式路由）

| 过滤 | 定长多槽列（MaxSlots ≥ 2） | 托管列表（MaxSlots = 0） |
|------|---------------------------|--------------------------|
| `WithRelationship<TRel>(target)` | chunk 扫描 + **逐槽校验**（`QueryEnumerable` 按列宽步进，任一槽 `Matches` 即命中，实测通过） | **⚠️ 返回空**（不占列 → `Archetype.IsMatch` 排除；候选集交集路径未实施）。反向查询请用 `GetRelationsOf<TRel>(target)`（O(1) 索引） |
| `WithAll<TRel>` | 拥有列即匹配（同单值关系） | 反向索引含该 relType 的实体（未实施，同上） |

> **设计修正（2026-09-05 实施时）**：托管模式的多值关系 `WithRelationship` 查询原设计为"反向索引候选集 → 与 chunk 扫描交集"，**未实施**（当前返回空）。原因是托管模式不占 chunk 列，查询过滤与列扫描路径耦合；正确的按 target 反向枚举用 `GetRelationsOf` 即可（O(1)）。如需托管模式原生查询过滤，需为 `QueryEnumerable` 增加独立候选集枚举路径（工作量 0.5-1 天），当前明确不做。

### 5.4 级联与销毁

| 时机 | 处理 |
|------|------|
| `DestroyEntityInternal` | 清正向列表 + 反向索引（扩展 `CleanupSourceRelations`，按 `IsMultiRelation` 分支） |
| `DestroyEntityCascade` | `CollectCascade` 已走反向索引（多值类型同样在索引中），列表侧对称清理 |

### 5.5 Job 边界（必须明示）

多值关系**不进 Job**：`[NativeTranspile]` Job 访问 → validator 编译期拦截（同 managed shared 的 NT0xx 报错路径，提示主线程读取）。这是托管存储的固有代价，与文档 `RelationMulti-多实例关系设计.md:60` 结论一致。

### 5.6 验收

| # | 项 | 方法 |
|---|----|------|
| 1 | 追加/幂等 | 同 target 重复 Add 不重复；`GetRelationships` 顺序与数量正确 |
| 2 | 反向查询 | `GetRelationsOf<Skill>(hub)` 返回全部持有者 |
| 3 | 查询过滤 | `WithRelationship<Skill>(skill)` 只返回持有该技能的实体；与 1:1 关系混合查询 |
| 4 | 级联 | `DestroyEntityCascade(target)` 销毁持有者；普通 `DestroyEntity` 清理列表 + 索引 |
| 5 | Job 拦截 | `[NativeTranspile]` Job 访问多值关系 → 编译期报错 |
| 6 | 防 ID 回收 | target 销毁（version+1）后列表内槽位失效 |

## 六、Phase 4：声明式级联（修复 P4）

### 6.1 设计

参考 Flecs `(Rel, OnDeleteTarget, EcsDelete)`，新增特性注册，**不改变 `DestroyEntity` 默认语义**（保持 S24 决策：默认不级联）：

```csharp
[AttributeUsage(AttributeTargets.Struct)]
public sealed class OnTargetDeletedAttribute : Attribute { public bool Cascade; }
// 用法：[OnTargetDeleted(Cascade = true)] struct ChildOf : IRelationComponent { ... }
```

- `DestroyEntity` 时：查该实体的关系类型集合（`oldArchetype.Types`），若存在 `[OnTargetDeleted(Cascade=true)]` 类型 → 走 `CollectCascade`（复用现有 DFS 防环逻辑）。
- 注册信息存 `ComponentTypeManager` 元数据（`CascadeOnTargetDeleted` bool 数组，同 `ComponentIsRelation` 模式）。

### 6.2 验收

| # | 项 | 方法 |
|---|----|------|
| 1 | 自动级联 | `[OnTargetDeleted(Cascade=true)]` 的父销毁 → 子自动销毁；无特性类型保持不级联 |
| 2 | 旧语义回归 | 现有 CascadeTests（含 `DestroyEntity_DoesNotCascade_ByDefault`）全量通过 |
| 3 | 防环 | 环状关系声明级联 → 不死循环 |
