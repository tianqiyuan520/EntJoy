# 标准 Chase-Lev 重构与尾部优化 — 实施记录（2026-08-22）

> 状态：**已合入**（`793fba2` → `1288cd6` → `cc36ac8` → `fd72cd2` → `839f74f` → `ef810ee` → `703760e` → `b870081`）
> 本文档记录从「共享认领注册表」重构为「标准 Chase-Lev」的完整历程：动机、方案、实测数据、关键决策。

## 一、动机：P99 尾部过大

原始数据（100K 实体，100 帧，15 worker，guided k=4 floor=16）：

| 指标 | 旧注册表版 | 目标 |
|------|-----------|------|
| BuildCore-Steady p50 | 0.583ms | ≤0.55ms |
| BuildCore-Steady p99 | **9.47ms** | ≤3ms |
| Query p99 | **9.14ms** | ≤3ms |
| Query max | 16.5ms | 低 |

**根因（逐路径分析）**：旧实现每次认领一片 tile 的开销是 MPMC 的 ~20 倍——

```
旧（共享认领注册表）:  PopBottom(mfence) → scan 256槽(highWater×3原子)
                       → claimers++/fetch_add/claimers-- (3 acq_rel RMW) → 内联执行
新（标准 Chase-Lev）:   PopBottom(mfence) → Injector.Pop(1 CAS) → 执行
```

`kMaxClaimableBatches=256` 槽 + `claimers` handshake + `highWater` 扫描 = 每个空闲 worker 每轮循环 `~20+ 原子操作`，15 worker 同时空转时竞争同一片 `claimSlots_` 内存 → cache line 颠簸。

## 二、重构方案：标准 Chase-Lev（crossbeam/TBB/Unity 模型）

### 2.1 删除（非标准组件）

| 组件 | 说明 |
|------|------|
| `claimSlots_[256]` | 共享认领注册表 |
| `claimers` handshake | 退役防 UAF 计数 |
| `RegisterBatch` / `UnregisterBatch` / `ClaimRange` | 注册表操作 |
| `g_chaseLevActiveBatches` + mutex | batch 追踪 |
| `activeTasks`（保留作 park 谓词） | 全局在飞计数 |

### 2.2 新增（标准组件）

| 文件 | 组件 |
|------|------|
| `MPMCInjector.h` | Vyukov MPMC 环形队列（32768），从 NativeWorkerPool 提取 |
| `RangeTaskPool.h` | 固定容量对象池（16384，Treiber stack） |
| 标准 WorkerLoop | PopBottom → Injector.Pop → StealTop(otherDeque) → Park |

### 2.3 关键实现点

```
SubmitBatch: 预切分 RangeTask → Injector.Push → 唤醒 worker
WorkerLoop:
  1. PopBottom(myDeque)              ← LIFO, owner-only, 零竞争
  2. injector_.Pop → PushBottom      ← 从 Injector 拉取推入 deque
  3. StealTop(otherDeque)            ← 1 CAS
  4. Park（有界自旋 → atomic::wait）
主线程 assist: TryAssistOne（Injector → steal worker deque）
```

**容量安全**：`kInjectorCapacity=32768`、`RangeTaskPool::kPoolSize=16384` 对 GridSearch（85 tasks/batch）余量 100x+；SubmitBatch 溢出时 `yield` 重试兜底。

**任务粒度**：kClaimBatchSize=4（tile/认领），实测 8/16 拖慢 GridSearch p50（破坏不规则负载均衡）——保持 4。

## 三、尾部优化历程（按提交顺序）

| 提交 | 改动 | 效果 |
|------|------|------|
| `793fba2` | 标准 Chase-Lev 重构 | p99 9.47→1.2-5.6ms（波动） |
| `6f3a5ad` | 主线程立刻 assist + 优先级 ABOVE_NORMAL | p99 3.2→1.1-1.4ms |
| `cfe79fa` | **撤销**优先级 hack → 主线程"先 assist 后 wait"持续兜底 + worker 有界自旋 | p99 1.0-1.2ms（**跨平台通用**） |
| `8845bde` | CPU 亲和性自适应（SMT→关绑定） | p99 0.85-0.97ms |
| `3c9676b` | 简化：亲和性默认关闭（去掉自适应） | 保持 0.85ms |
| `78df1fc` | assist 默认关闭 + 显式 API（`SetMainThreadAssistEnabled`/`SetWorkerAffinityEnabled`） | 保持 0.85ms |

### 3.1 各优化贡献量化

| 改动 | BuildCore p99 | 性质 |
|------|--------------|------|
| 基线（注册表版，无 assist 优化） | 9.47ms | — |
| 标准 Chase-Lev 重构 | 1.2-5.6ms | 架构级 |
| + 主线程立即 assist | 3.2ms | 架构级 |
| + 优先级 ABOVE_NORMAL | 1.1-1.4ms | ⚠️ hack（不通用） |
| **+ 主线程"先 assist 后 wait"（撤优先级）** | **1.0-1.2ms** | ✅ 通用 |
| **+ 亲和性默认关（SMT）** | **0.85-0.97ms** | ✅ 通用 |

### 3.2 关键洞察（为什么这些改动有效）

1. **主线程 assist 的"停顿窗口"是 p99 主因**：原 `Complete()` 等 1ms condvar 超时才 `TryAssistOne`。慢 worker 被 OS 抢占时，主线程干等 → 整批卡 1ms+。改为 spin 阶段每 16 次 + Phase 3 **先 assist 后 wait**（`kCompleteRevisit=1ms→256µs`），主线程成为持续工作的第 N+1 个执行者。

2. **SMT 机器上固定亲和性 = 每物理核心 2 线程死绑**（AMD 8845H 8物理16逻辑）：worker 绑逻辑 1-15，逻辑 0-7=SMT0(物理0-7)、8-15=SMT1(物理0-7) → 每个物理核心 2 线程共享执行单元/缓存。实测绑定 p99 1.0-1.2ms vs 不绑定 0.8-0.9ms。默认关闭亲和让 OS 自由调度，配合主线程 assist 兜底。

3. **有界自旋只读 activeTasks/own stamp（零竞争）**：worker 在 `Complete→Schedule` 批间隙自旋 2048 次（~90µs）检测新批唤醒，不碰 deque/Injector（避免 15 worker 竞争）；超时/activeTasks==0 仍 park 防空转。

### 3.3 已尝试但失败的方案（防重踩）

| 方案 | 结果 | 原因 |
|------|------|------|
| `kParkSpinMax=256/2048` 自旋内找活 | p50 0.55→0.9-1.3ms | 自旋内 PopBottom/Steal 造成 15 worker 竞争 |
| 自旋窗 16384（~700µs） | p99 2.7-7ms | worker 烧 CPU 不减抖动（OS 调度固有） |
| assist 优先偷 progress 最小 worker | p99 0.85→0.96-1.38ms | GridSearch 所有 worker 活跃，progress 差异小；扫描开销 + 抢空 deque |
| worker=8（物理-1） | p50 0.74（升 25%） | 吞吐损失换尾部，非正解 |
| 优先级 ABOVE_NORMAL | 有效但撤销 | 不通用（Linux/macOS 需特权） |

## 四、最终配置与 API

### 4.1 默认配置（对齐 Unity 纯 worker 模式）

```
worker        = 逻辑核心-1（15）    ← 总线程-1，多线程吞吐最优
CPU 亲和性     = 默认关闭            ← OS 自由调度（SMT 机器最优）
主线程 assist  = 默认关闭            ← 纯 worker，实测与开启相当
worker 自旋    = 有界 2048 次        ← 覆盖批间隙
guided        = k=4 floor=16
```

### 4.2 运行时 API（C#）

```csharp
NativeJobScheduler.SetMainThreadAssistEnabled(bool);  // 开关主线程 assist
NativeJobScheduler.SetWorkerAffinityEnabled(bool);     // 开关 CPU 亲和性
NativeJobScheduler.SetGuidedEnabled(bool);              // 开关 guided tile 调度
```

环境变量已删除（`ENTJOY_ASSIST` 等），所有开关统一由 API 控制。

## 六、S1-S5 基准影响（JobLibsBenchmark，中位数）

| 场景 | 旧 Chase-Lev | 标准 Chase-Lev | 说明 |
|------|-------------|---------------|------|

- **尾部优化不体现在 S1-S5**：它们取中位数；尾部（p99）指标由 GridSearch 专项衡量。

## 七、后续方向（未排期）

1. **Query 残余尖峰**（max 5.4ms）：TempJob 分配缺页（`SearchClosestPoint` 每帧 new 400KB NativeArray）→ 采样端池化可消除。

## 八、调试器改进（2026-08-22）

### 8.1 M 道 HeavyJob 段修复
**问题**：`ENTJOY_ASSIST` 环境变量未设置时（空字符串），`value != "0"` 对空串 true → `g_mainThreadAssistEnabled` 被误设为 true → 主线程 TryAssistOne 执行 HeavyJob tile → M 道出现非直调段。

**修复**：删除 ENTJOY_ASSIST 环境变量解析，仅由 `JobSystem_SetMainThreadAssist` API 控制，默认 false。

**验证**：`[SEG-M]` 诊断输出从 21 条降为 0（HeavyJob 不再出现在 M 道）。

### 8.2 ChaseLev 调试计数器补全
旧 MPMC 路径的 `AssistExecuteOneTile` 更新了4个计数器，但 ChaseLev 的 `StealAndExecute` 遗漏了2个。修复后：

| 计数器 | ChaseLev 更新位置 |
|--------|-------------------|
| `g_assistExecuted` | StealAndExecute Injector + deque 路径 |
| `g_mainExecutedRanges` | StealAndExecute Injector + deque 路径 |
| `g_assistTiles` | StealAndExecute Injector + deque 路径 |
| `batch->batchAssistTiles` | StealAndExecute Injector + deque 路径 |
| `g_localTiles` | ExecuteAndRelease（worker 路径）+ WorkerLoop PopBottom/StealTop |
