# Chase-Lev Deque 重构实施历程与问题分析（2026-08-21）

> 状态：**已收敛**。依赖链 105 轮偶发死锁（~11/30）根因已定位并修复：
> `SparseTileDeque::PopBottom` 缺 crossbeam 的 SeqCst fence，x86 store→load 重排
> 导致 owner 与 thief 双认领同一槽位（双执行）。修复后压测 100/100 通过。
> 本文档记录从计划到实施的全过程：每次改动的设计意图、死锁症状、根因分析、
> 修复尝试与最终结论。目标读者：后续接手重构的开发者（含 AI agent）。

---

## 一、目标架构回顾

原始计划（见 `20260821-Chase-Lev-Deque-重构计划.md`）：
将 NativeWorkerPool 从「全局 MPMC 环形队列 + 共享 `nextTile.fetch_add(4)`」改为
「每 worker 一个 Chase-Lev Deque + 工作窃取」。

**关键前提**（实施中反复踩坑后确认）：Chase-Lev 论文的标准模型是——

```
每个 worker 持有一个 Deque（owner-only PushBottom/PopBottom）
跨线程提交（主线程 / 依赖 continuation 的 worker）→ 入口队列（Injector）
worker 从 Injector 拉取到自己的 Deque → 标准 Chase-Lev 循环（PopBottom → StealTop）
```

这与 crossbeam-deque / TBB / Unity Job System 一致：
- **Chase-Lev Deque 解决「worker 之间窃取」**（LIFO 本地 / FIFO 窃取）
- **入口队列解决「跨线程提交」**（否则多生产者 push 违反 owner-only 前提）

## 二、实施历程（按时间顺序）

### Phase A：SparseTileDeque 基础实现 + 单测

**文件**：`src/NativeDll/SparseTileDeque.h`（新建）、`src/NativeDll.Tests/SparseTileDequeTests.cpp`（新建）

**设计**：Chase-Lev 风格有界 deque，容量 2 的幂，`top_` 原子 / `bottom_` 非原子（owner-only）。

**修复的 bug**：
1. `PopBottom` 最后一个元素 CAS 成功后缺少 `bottom_ = t + 1`
   —— `bottom_` 滞后于 `top_`，后续 push 写入位置在 `top_` 之前，thief 永远看不到。
   这是 Chase-Lev 论文的关键一行，缺失导致并发测试丢任务。
2. 并发测试死锁（`TestHighFrequencyAbaStress` / `TestConcurrentStealRounds`）：
   原因是在 `std::async` 测试包装里线程自旋无 yield 导致调度饥饿，非算法 bug。
   修复：thief 空转加 `std::this_thread::yield()`。

**结论**：单测全绿（单线程 / 多线程 / last-element race / ABA 压力 / capacity 对齐）。

### Phase B：per-batch Deque 方案（错误方向 1）

**设计**：每个 batch 分配 `workerCount` 个 `SparseTileDeque`，tiles round-robin push，
worker 从自己的 deque PopBottom / 跨 worker StealTop。

**崩溃**：`0xc0000005`（访问违规）。
**根因**：`AssistExecuteOneTile` 仍用 `batch->nextTile.fetch_add(1)` 认领 tiles，
与 deque 中的任务**双重执行** → 状态损坏。

**性能退化**：S5 8.259ms（目标 ≤4.3ms）。
**根因**：per-batch 创建/销毁 15 个 deque + 1000 次 push/batch，
S5 10 万 batch 级联放大分配开销。

**结论**：per-batch 分配是错误方向。Deque 必须是 worker 生命周期的持久资源。

---

### Phase C：持久 per-worker Deque（错误方向 2）

**设计**：`WorkerState` 持有 `unique_ptr<SparseTileDeque>`（worker 生命周期），
SubmitBatch 直接把 tiles round-robin push 进各 worker 的 deque。

**死锁**（偶发，1/3~1/6 概率）：所有 worker 空闲、deque 空，但 batch 未退役，
`g_backendBatchesOutstanding` 永不归零 → `WaitForBackendBatches` 死锁。

**根因（关键）**：`SubmitBatch` 可从任意线程调用（主线程直接提交 / worker 线程执行
依赖 continuation 时再提交），且都向**所有 15 个 worker 的 deque 并发 PushBottom**。
这**违反 Chase-Lev 的 owner-only 前提**——`bottom_` 非原子，多生产者并发写 =
数据竞争 → 任务悄悄丢失。

**修复尝试**：`TileTask` 从 `{tileIndex}` 改为 `{batch*, firstTile, tileCount}`
（携带 batch 指针，跨 batch 混存时 thief 能正确执行）——修复了 batch 指针错误，
但**没有解决多生产者 push 的数据竞争**。

**结论**：必须引入入口队列。Chase-Lev Deque 本身不支持多生产者 PushBottom。

---

### Phase D：全局 MPMC 入口队列（crossbeam Injector 模型）

**设计**：`ChaseLevScheduler` 持有全局 MPMC 环形队列（Vyukov 算法）作为入口。
SubmitBatch（任意线程）push 任务进 MPMC → worker 批量拉取到自己的 deque
（owner-only PushBottom）→ 标准 Chase-Lev 循环。

**正确性验证**：`ChaseLevIntegrationTests`（新建，含 ParallelFor / Chunk / 依赖链 /
105 轮重复依赖链）**20/20 全过**。

**性能问题**：GridSearch 构建 0.780ms → 2.784ms（哈希计数/元素放置 phase 慢 5 倍）。
**根因**：全局 MPMC 是单点热点——15 个 worker 抢同一个 `dequeuePos` CAS + 缓存行颠簸。
任务密集的 phase 被放大。

**期间修复的深层 bug**（依赖链 105 轮偶发死锁）：
1. **use-after-free**：batch 退役时（tilesRemaining==0）worker 的 deque 里可能还持有
   该 batch 的任务 → `ReleaseBatch` 后 task.batch 悬垂。
   → 引入 `pendingTasks` 计数：退役需 `tilesRemaining==0 && pendingTasks==0` 双条件，
     由「最后完成者」（最后一个 tile 或最后一个 task）执行退役。
2. **StealTop CAS 后校验 bug**：初版在 CAS 成功后 acquire 校验 seq，校验失败时
   `top_` 已推进但任务未拿走 → **任务永久丢失**（tilesRemaining 下溢 -3）。
   → 改为 **CAS 前** acquire 校验（对齐 crossbeam-deque 的 stamp 校验）。
3. **double release**：`TryFinalizeChaseLevBatch` 里 `ReleaseState(state)` 在
   `finalized.exchange` 块外——最后一个 tile 完成者和最后一个 task 完成者同时通过
   双条件检查时，两者都执行 ReleaseState → use-after-free。
   → `ReleaseState` 移入 `finalized.exchange` 成功块内。

**结论**：MPMC 入口在**正确性**上可行，但**性能**上失败（全局热点）。

---

### Phase E：per-worker MPSC 注入队列（分散竞争）

**设计**：把全局单个 MPMC 改为**每 worker 一个 MPSC 注入队列**（Vyukov 序列号）。
SubmitBatch round-robin 分发到各 worker 的注入队列（生产者 CAS 分散到 15 个队列），
每个 worker 只消费自己的（**单消费者零 CAS 竞争**）。

**性能**：注入竞争分散 15 倍，消除全局热点（预期恢复 GridSearch 性能）。

**期间引入的新死锁**（偶发，~5/20）：
1. **线程亲和 bug**：初版用 `WorkerIndexManager::GetCurrentIndex()` 判断调用者是否为
   本池 worker（依赖 continuation 场景），但主线程/其他线程也可能被分配过 index
   （旧路径 AllocateIndex）→ 主线程误判为 worker → 往他人 deque PushBottom →
   违反 owner-only → 数据竞争。
   → 改用 `thread_local bool t_isPoolWorker` 精确标记本池 worker 线程。
2. **parked 唤醒竞态**：只唤醒 parked worker 的优化与 `WaitForSingleObject` 之间存在
   竞态窗口（worker 检查完队列 → park 前 SubmitBatch 读到 parked=0 → 不 SetEvent →
   任务滞留 1ms+，依赖链下累积成死锁）。
   → 回退为全唤醒（可靠）。

**A/B 验证**：无线程亲和 + 全唤醒 + per-worker MPSC → **20/20 全过**。

**结论**：per-worker MPSC + owner-only Deque + 全唤醒 是稳定且性能正确的组合。

---

### Phase F：纯 Chase-Lev 并发 PushBottom（错误方向 3）

**用户反馈**：明确要求「完全按照 Chase-Lev Deque 实现，MPMC 框架不使用」。

**尝试**：去掉入口队列，`SparseTileDeque::PushBottom` 改为并发安全
（`bottom_` 原子 + CAS），SubmitBatch 直接 round-robin push 到各 worker deque。

**结果**：**30/30 全死锁**。
**根因**：Chase-Lev 的孤儿元素协议（PopBottom 预减 bottom_ 后与 StealTop 竞争
最后一个元素）假设 **owner 不会在自己 pop 时 push 同一个槽**。并发 PushBottom 打破
该假设：PopBottom CAS `bottom_ b→b-1` 成功后，另一线程 PushBottom 可能 CAS
`bottom_ (b-1)→b` **覆盖同一槽** → 旧数据丢失或读到半写数据。

**结论（重要）**：**Chase-Lev Deque 在数学上不支持多生产者 PushBottom**。
所有主流实现（crossbeam / TBB / Unity）都通过入口队列（Injector）解决跨线程提交。
「完全不用入口队列的纯 Chase-Lev」不可行。

---

### Phase G：回到 crossbeam 标准模型（当前状态）

**设计确认**（与用户对齐）：crossbeam 标准模型 = **每 worker 一个 Chase-Lev Deque
（owner-only）+ 每 worker 一个 MPSC 注入队列（Injector）**。这正是 C++ 高性能库
（TBB/Rayon）与 Unity Job System 的实现方式。

**当前实现**：
- `SparseTileDeque.h`：owner-only PushBottom/PopBottom + StealTop（CAS 前 seq 校验）
- `ChaseLevScheduler.{h,cpp}`：每 worker Deque + MPSC 注入队列 + 全唤醒
- `JobSystem_Tiles.cpp`：`SubmitBatch` 双路径（ChaseLev / 旧 NativeWorkerPool）、
  `TryFinalizeChaseLevBatch` 双条件退役、`ChaseLevExecuteTile`/`ChaseLevTaskDone` 回调

**当前状态**：依赖链 105 轮压测仍偶发死锁（~11/30），正在收敛。

### Phase H：根因定位与修复（2026-08-21 晚，本会话完成）

**诊断方法**（逐层加探针，最终由任务身份追踪一锤定音）：
1. **在飞 batch 注册表**（`g_chaseLevActiveBatches` + `DebugDumpChaseLevState`）：
   死锁时打印每个未退役 batch 的 `tilesRemaining`/`pendingTasks`，区分
   「任务没执行完（tr>0）」与「执行完但退役被跳过（tr==0 && pt>0）」。
   结果：batch N 的 tr=0xFFFFFFFC（**下溢 -4**）、pt=0xFFFFFFFF（-1），
   batch N+1 的 tr=4、pt=1 —— 既有任务**多执行了 4 个 tile / 1 次 taskDone**，
   又有任务**少了 4 个 tile / 1 次 taskDone**（同一次事故的两面）。
2. **任务身份追踪**（`TileTask.taskId` + 环形 TraceTask 'P'/'C'/'S'/'E'/'D'）：
   抓到决定性证据 —— 同一 taskId 被 **PopBottom（owner）与 StealTop（thief）各认领一次**，
   **执行两次**；同时该 worker 注入队列里另一个任务被 push 后**从未被 pop**
   （其槽位数据被重复派发的任务"顶替"）。全局计数（pushed==popped==exec==done==3481）
   完美平衡 —— 说明不是"任务丢失"，而是**同一槽位被两人认领**。
3. **逐 worker 任务流计数**（injP/injC/dqP/dqC/dqS/exec）排除注入队列重复派发
   （`CheckInjectPopAnomaly` 全程未触发：同队列从未重复 pop 同一任务）。

**根因（最终结论）**：`SparseTileDeque::PopBottom` 的原子序缺陷 ——
**x86 store→load 重排**。代码序列：

```cpp
uint64_t b = bottom_ - 1;
bottom_ = b;                                    // 普通 store，滞留 store buffer
uint64_t t = top_.load(std::memory_order_acquire); // acquire 不阻断"本 load 提前于前序 store 执行"
```

`bottom_ = b` 是普通 store；紧随的 `top_.load(acquire)` 可被 CPU **提前执行**
（x86 允许 store→load 重排，acquire 只约束 load 之后的指令，不约束 load 之前的
store），读到**陈旧**的 top_。于是：

- owner 读到旧 top_=p，把 b=p+1 判为"非最后元素"（b > t），**无 CAS 直接取走**；
- 另一 thief 此前读过旧 bottom_=p+2（在 owner 的 store 生效前），其 StealTop 的
  CAS（top_ p+1→p+2）**成功**，也认领了 p+1 —— **双认领 → 双执行**；
- 被"顶替"的任务（push 了但槽位数据被覆盖）永不执行 → tr/pt 永不归零 → 死锁。

**修复（对齐 crossbeam-deque v0.8）**：crossbeam 在 `back.store(b)` 与
`front.load()` 之间插入 `atomic::fence(Ordering::SeqCst)`（阻断 x86 store→load
重排）。`SparseTileDeque::PopBottom` 补上同一 fence：

```cpp
uint64_t b = bottom_ - 1;
bottom_ = b;
std::atomic_thread_fence(std::memory_order_seq_cst);  // 【修复】阻断 store→load 重排
uint64_t t = top_.load(std::memory_order_acquire);
```

fence 使 owner 的 top_ load 在 bottom_ store 落盘后执行：若 thief 已认领 b，
owner 读到 t > b → 判空返回；若 b 仍未被认领，owner 的 b==t 判定必然走
最后元素 CAS 路径与 thief 竞争（单一仲裁）。**两种时序都消除双认领**。

**验证**：
- 修复后依赖链 105 轮压测 **100/100 × 2 批全过**（原代码 ~11/30 死锁）；
- `SparseTileDequeTrace`（自带 DUP 检测：owner/thief 双执行检测）**lost=0、无 DUP**；
- `SparseTileDequeTests` / `SparseTileDequeSmoketest` 全过；
- `JobSystemTests` 仅剩文档记载的既有失败 `trace claim count mismatch`（与本次无关）。

**调试代码去留**：诊断期加的重型探针（2048 槽任务追踪、双执行检测环、注入队列
异常环、deque 双认领检测）已全部移除（其 O(n) 扫描会把压测放慢 ~5 倍、改变调度
时序）。保留：per-worker 任务流计数（injP/injC/dqP/dqC/dqS/exec，每任务 1 次
relaxed fetch_add，开销可忽略）与在飞 batch 注册表（batch 级 2 次互斥锁操作），
供后续死锁/调试面板使用。`TileTask.taskId` 因无消费者已移除。

## 四、关键设计结论

1. **Chase-Lev Deque = owner-only**。PushBottom/PopBottom 只允许 owner worker 调用。
   跨线程提交必须走入口队列（Injector）。这是不可妥协的正确性约束。

2. **入口队列的选择**：
   - 全局 MPMC：正确但全局热点（性能差）
   - per-worker MPSC：竞争分散、单消费者零 CAS，**正确且性能好**（推荐）

3. **生命周期管理**：batch 退役必须满足双条件
   `tilesRemaining==0 && pendingTasks==0`，由最后完成者执行，
   `ReleaseState` 必须在 `finalized.exchange` 成功块内。

4. **StealTop 的 seq 校验必须在 CAS 前**（而非 CAS 后）——否则 top_ 已推进但任务丢失。

5. **PopBottom 必须阻断 x86 store→load 重排**：`bottom_ = b`（普通 store）后紧跟
   `top_.load()` 时，必须在两者之间插入 `std::atomic_thread_fence(seq_cst)`
   （crossbeam 的 `back.store(b, Relaxed); fence(SeqCst); front.load(Relaxed)`）。
   acquire 只约束 load 之后的指令，**不约束 load 之前 store 的执行顺序**——缺 fence
   会让 owner 读到陈旧 top_，与 thief 双认领同一槽位（本实现终局死锁根因）。

6. **唤醒策略**：全唤醒可靠；parked 选择性唤醒需解决竞态窗口
   （worker 检查完队列 → park 前的窗口）。

## 五、遗留问题（当前状态）

1. **依赖链 105 轮偶发死锁（~11/30）——【已修复】**：根因是 `SparseTileDeque::PopBottom`
   缺 crossbeam 的 SeqCst fence（x86 store→load 重排 → owner/thief 双认领同一槽位 →
   双执行 + 任务被顶替）。修复后压测 200/200 通过（详见 Phase H）。
   诊断期重型探针已移除；保留 per-worker 任务流计数与在飞 batch 注册表供后续排查。

2. **性能对比**：per-worker MPSC 方案尚未跑完整 S1-S5 + GridSearch 基准。
   预期恢复（vs 全局 MPMC 2.78ms），待验证。fence 仅加在 PopBottom 一处、
   单条 mfence（非热路径 CAS），对吞吐影响预计可忽略。

3. **调试面板统计**：ChaseLev 路径的 `g_workerExecutedRanges` 等全局统计未接线
   （worker 执行任务未递增这些计数器），面板数据可能失真。

2. **回归来自 Chase-Lev 调度架构本身**，且**越轻/越细粒度越明显**（S2 +50%、
   GridSearch Query ~2x），重计算场景（S5/S3）被摊销无感。
3. **根因**：旧路径每个 work-item 是一个粗粒度 batch，worker 用

   Pop、逐任务 pendingTasks/taskDone 记账、可能的 steal 扫描与 1ms park/wake。
4. **任务粒度不是杠杆**：`kTasksPerWorker` 1（15 粗任务）→ GridSearch Query 3.46ms
   （负载失衡更差）；4→~1.0ms；`ENTJOY_BENCH_TPW` 1/4/16/64 sweep 均在 0.97–1.26ms。
   旧路径同 sweep 恒 ~0.58–0.74ms —— 动态认领 vs 固定任务切分是差距本质。
5. **GridSearch 不是纯并行批**：Query = 每次一个 100k 查询 job（Hash 查找逐 query
   开,cell 密度不均），恰是"动态认领"受益的负载；Chase-Lev 固定切分丢失该增益。

### 待办（如需追平）

- 方案 A（低风险）：Chase-Lev 任务内叠加动态子块认领 —— worker 执行范围任务时

- 方案 B：轻/细粒度 job 走旧路径，重 job 走 Chase-Lev（混合调度，复杂度高）。
- 方案 C：接受回归 —— Chase-Lev 已达成其设计目标（S5 方差收敛、无全局热点），

## 附 2：性能修复（2026-08-21 晚，提交 `37a6c74`）

### 根因（实测确认）

"每 worker 私有 MPSC 注入队列"是**非标准** Chase-Lev 集成（标准是"共享 Injector +
本地 deque + 窃取"，crossbeam/TBB/Rayon/Unity 均如此），带来两个退化：

1. **尾延迟爆炸（GridSearch max 28ms vs MPMC 2.8ms）—— AI 分析正确**：
   `WorkerLoop` 只消费自己队列、只窃取别人 deque（`ChaseLevScheduler.cpp` 旧 249-294）。
   慢 worker（被 OS 抢占 ~28ms）的 4 个任务锁死在**私有注入队列**，其他 14 worker
   无法窃取、全部空转 → 整 batch 卡到慢 worker 醒来。
2. **p50 ~2x 回归（GridSearch Query 0.97-1.26 vs 0.54-0.68）**：固定 60 任务

`SubmitBatch` 不再预切分任务进私有队列，而是把 batch 注册进**共享认领表**；
worker 用 `batch->nextTile.fetch_add(kClaim=4)` **动态认领**一片推入自己 deque 执行。

- 无全局队列 dequeue 争用：认领分散到各 batch 的 relaxed fetch_add。
- **UAF 防护（AI 方案遗漏的临界）**：认领前 `slot.claimers++` 并重读注册槽；
  退役方 `UnregisterBatch` **先清槽再等 claimers==0 再 ReleaseBatch**——退役临界内
  无 worker 正在认领，杜绝"认领持有已回收 batch 指针"。

### 对"三步微调"方案的核实（拒绝理由，防重踩）

| # | 提议 | 结论 | 拒绝理由 |
|---|---|---|---|
| 1 | PopBottom 的 seq_cst fence 降级 release | ❌ 拒绝 | x86 允许 store→load 重排，release 在 x86 无 mfence，挡不住硬件重排 → 复活依赖链死锁（Phase H 根因）。且实测 fence 成本 ≈0（移除后 GridSearch 不变）|
| 2 | claimers 移到 BatchState | ❌ 拒绝 | claimers 必须在常驻注册表槽上：`batch->claimers++` 先解引用 batch 指针，若槽正被清、batch 正在退役回收 → UAF。现协议靠"槽常驻 + 重读槽指针"才安全。无性能收益（同一缓存行争抢不变）|
| 3 | 认领后直接执行首 tile、其余逐个推 deque | ❌ 拒绝 | 误读代码：现路径一次认领是**一个范围任务**（1 次 Push + 1 次 Pop + 执行 4 tile + 1 次 taskDone），非每 tile push/pop。AI 方案拆成每 tile 任务反而多 3 次 push + 记账变更 |
| 附 | kClaimBatchSize 4→8/16 | ❌ 拒绝 | 实测拖慢 GridSearch Query p50（0.56→1.0+）：粗粒度破坏不规则负载均衡 |

### 遗留

- **S2 空任务仍 ~+10%**：纯空任务下 Chase-Lev 的认领/pop/taskDone per-task 开销
  vs 旧路径紧 `fetch_add` 空循环。微基准不代表真实负载；如需追平可对"空 job"

## 附 5：采纳旧 MPMC 动态认领设计 —— S5 追上/超越 Misaki（提交 `a38f9d1`）

### 旧 MPMC 的优秀设计盘点（可采纳项）

| # | MPMC 设计 | 采纳状态 |
|---|---|---|
| 1 | **动态认领 `nextTile.fetch_add(k)=4` 内联执行**（1 原子/认领，无 deque 往返）| ✅ **已采纳**（见下）|
| 2 | 混合等待（8192 自旋 → semaphore）| ❌ 实测共享注册表下负收益（见附 3）|
| 3 | Relaxed TrySteal（允许偷 OS 延迟 worker 的活）| ✅ 共享注册表全员可认领，天然具备 |

### 采纳方式（Chase-Lev 内联首 tile，保留可窃取性）

认领 `[s, s+k)` 后：
- **首 tile s 由本 worker 内联执行**（省 1 次 PushBottom+PopBottom+mfence）

- 记账守恒：一次认领 = 一个范围任务；`cnt>1` 时 taskDone 由剩余任务覆盖整次
  认领；`cnt==1` 时内联执行后立即 taskDone（否则 pendingTasks 永不归零）

## 附 7：主线程协助执行（assist）—— 对齐旧 MPMC 的第 16 个执行者（提交 `2910822`）

### 根因（用户关键线索）

用户指出旧 MPMC 的三大特征：**大块 tile + guided + assist**，且 MPMC 多次运行
稳定（核心耗时 ≤0.7ms、max ≤3ms）。核查代码发现 Chase-Lev 路径**禁用了 assist**：

```cpp
// JobSystem_State.cpp（旧）
static bool AssistState(...) { if (g_useWorkStealing) return false; }  // ← 禁
// JobHandle::Complete
if (g_useWorkStealing) goto wait_for_completion;   // ← 主线程纯等待
```

MPMC 里主线程是第 16 个执行者（等待期间持续认领+执行）——当 15 个 worker 中
任一握着"最后一片"被 OS 抢占 30ms，主线程能认领兜底；Chase-Lev 只有 15 worker
干等 → 整批等慢 worker → p99 19ms / max 32ms。

### 实现

- `ChaseLevScheduler::TryAssistOne()`：主线程扫描共享认领表 → claimers handshake
  （与 worker 完全一致，防 batch 退役 UAF）→ `ClaimRange` 认领一片 → 内联执行
  整片 → `taskDone` 一次（记账与 worker 相同）
- `Complete()` 等待循环内调用（Phase 3 每 1ms 回访）；**有界每轮 16 片**——
  初版无界 `while(TryAssistOne())` 在链条级联时主线程无限 assist 不回查
  completed（1/20 超时），有界后 30/30

### 实测

| 指标 | 修复前 | 修复后 |
|---|---|---|
| S5 高竞争 Native | 3.85 中位 | **3.53-3.64ms（Misaki 3.94-4.30，快 10-15%）** |

## 附 8：对照 C++/C# 高性能框架的调度设计（2026-08-21 晚）

### 已逐行核对的框架等待模式

| 框架 | 等待模式 | 关键点 |
|---|---|---|
| **enkiTS**（Doug Binks）| `spinCount>10 → WaitForNewTasks(信号量 INFINITE)`；否则 `SpinWait(spinCount*100 rdtsc)` 递增退避 | 短退避自旋 → 信号量精确阻塞；无轮询 |
| **Misaki**（C#）| `for(i<25){ SpinWait.SpinOnce(-1); if(HasWork())break; } WaitForWork(SemaphoreSlim)` | 25 次短自旋 → 计数信号量精确唤醒；注释明言锁开销损失 0.03ms |
| **tejchid/job-system** | `cv.wait(runnable_>0)` 谓词 + notify_one | 全局计数谓词自愈，无唤醒竞态 |
| 我们（当前）| `wakeEpoch.wait(旧epoch)`（`e60d92d`）| C++20 atomic::wait ≈ 信号量+谓词，无 Reset 丢失窗口 |

### 已实现的等价项

- **短自旋 → 阻塞**：Misaki/enkiTS 的自旋是"避免快速 case 的系统调用"，本质仍靠
  精确唤醒；我们的 epoch notify_all（1 次 futex）已等效。实测 96 短自旋（跳过
  PopBottom 版）无稳定收益，回退保持 0（机器噪声下不可测）。
- **assist**（`2910822`）= Misaki FindJob 的主线程等价；**inline-first-tile**
  （`a38f9d1`）= enkiTS 的 ExecuteRange 直跑。

### 残余尾延迟的判定

GridSearch Query 偶发 max 3-18ms（本机噪声段实测），**同分钟旧 MPMC 也 12-46ms**：
残余尖峰 = OS 调度 15 线程 + COLD 分配缺页（Steady 路径 p99 稳定 1.1ms 佐证），
两框架同样存在（S5 文档：所有库 ±24-60% 波动重叠）。调度侧已无可复现优化项。

## 附 9：自适应唤醒 —— 按任务量只唤醒需要的 worker（提交 `6f62f7d`）

### 动机

每 batch 全广播唤醒 15 worker：小 job（1-2 tile，如 GridSearch 前缀和/填充）也
全醒，14 个 worker 醒来发现没活再睡 = 每次 15 次 OS 唤醒浪费。

### 实现（对齐 Misaki `SemaphoreSlim.Release(N)` + tejchid `runnable_` 谓词）

- per-worker `wakeStamp[i]` + round-robin 游标；`needWake = ceil(taskCount/kClaim)`
  （每 worker 至少消化 kClaim 片的充足上界），仅唤醒前 N 个 worker
- **自愈保证**：`activeTasks>0` 时 worker 不 park（WorkerLoop 4.5）→ 任何"有活"
  时刻至少一个醒着的 worker 在循环消费 → 只唤醒 N 个不会丢任务/死锁
- 这是 `09806fb` 选择性唤醒失败的修复：当时无 activeTasks 谓词（无自愈），
  部分 worker 沉睡 + 1ms 轮询兜底 → 任务滞留累积

### 测量

正确性 25/25 + 15/15（105 轮依赖链）。Cold p99 中位 ~3.0ms（机器噪声大，无
回归证据）；Query 大 job needWake=15 不受影响。S5 高竞争不受影响（单 job
全醒）。

## 附 10：去 claimers 实验（2026-08-21 晚，结论：保留 claimers 更安全）

### 尝试

把认领游标 `nextTile` 从 batch 移到**常驻 ClaimSlot**，去掉 claimers handshake：
每次认领从 3 次 RMW（claimers++/fetch_add/claimers--）降为 1 次 RMW + 1 次
清槽校验 load。安全论证尝试：
- slot 常驻 → fetch_add 无 UAF；
- start < tileCount ⟹ 该片未执行 ⟹ tilesRemaining>0 ⟹ 未 finalize ⟹ batch 存活；
- fetch_add 后重读 slot.batch 确认未清槽再读 batch 字段。

### 结果

**30 轮压测仍偶发失败（1/30）**——存在我无法闭合的罕见交错窗口（清槽与
tileCount 读取之间）。claimers handshake 正是为闭合这类窗口而存在。**已回退**
至提交 `6f62f7d`（claimers 版，15/15 稳定）。

### 结论

- 减少认领原子数（3 RMW → 1）的收益被正确性风险抵消——claimers 是防批量
  退役 UAF 的必要 handshake，不宜移除。
- 若真要降低认领竞争，方向是**每 worker 本地批量认领**（一次 claimers 持有
  期间连续 fetch_add 多片，摊薄 handshake 次数），但这与"单片认领的均衡性"
  冲突（此前 kClaimBatchRanges=4 实测拖慢 p50），且 sticky 实验（附 8 未收）
  在复杂 harness 下不稳定。调度侧已到保守收敛点。

## 附 11：轻任务开销修复实验（2026-08-21 晚，结论：架构性差距，非调度参数可解）

### 现象（用户 ECS 对照）

IJobChunk 100w 轻量移动：MPMC 第一轮 0.188ms vs Chase-Lev 0.446ms（2.4x）。
复测 Chase-Lev 0.362 反超——**该 sample 长时测量受机器噪声影响 ±3x，单次
对照不可信**；但"轻任务高频认领下 Chase-Lev 每片 3 RMW 偏贵"的模式信号真实
（对齐 S2 空任务 0.305 vs MPMC 0.248）。

### 尝试（全部实测失败，已回退）

| 方案 | 结果 | 根因 |
|---|---|---|
| 去 claimers（nextTile 入 slot）v1 | 30 跑 1 失败 | 退役时序竞态 |
| 去 claimers v2（fetch_add→重读槽→读 tileCount） | 50 跑 8 失败 | **0xC0000005 真 UAF**：executor_ 内最后一个 tile 执行完触发最终退役释放 batch，worker 返回后仍 deref b |
| 去 claimers v3（游标先复位再发布） | 50 跑 10 失败 | 同上（UAF 本质未除）|
| 安全粘性认领 v2（每片独立 claimers + 执行后只读 slot） | 单测 50/50 ✅，GridSearch 不再挂 | **GridSearch p50 回归 0.58→0.73（垄断），ECS 1.14 vs 0.36（更差）**——动态粘性认领破坏负载均衡 |

### 结论

1. **claimers 不可移除**（UAF 本质）：`executor_` 执行最后一个 tile 会同步触发
   `finalize → UnregisterBatch → ReleaseBatch`，执行返回后 batch 已释放；claimers
   确保执行与退役的握手，是防 UAF 的必要防线（不是"多余的 2 次 RMW"）。
2. **动态粘性认领不可行**：共享注册表模型下丢均衡（与 MPMC"提交时静态分块"
   根本不同——MPMC 分块发生一次，我们的粘性让单 worker 连续吃片）。
3. **轻任务差距是架构性**：MPMC 静态大分片 1 次分配 vs Chase-Lev 每片 3 RMW，
   除非按 job 类型路由静态路径（如 IJobChunk 轻任务走大块），否则调度参数
   无法抹平。**列为后续可选：按 job 特征（tileCount/workerCount）选择
   static-slice vs dynamic-claim**。

## 附 12：C++ 异常协议 + 性能零影响验证（提交 `aba667b`）

### 协议（对齐 TBB/Taskflow 语义）

C++ 项目可直接使用 `JobSystem.h`（纯 C++ API：`Scheduler::Initialize /
Schedule/ScheduleParallelFor / JobHandle::Complete`），补上工业级异常契约：

- `BatchState` 记录首个回调异常（atomic CAS guard）；`TryExecuteOneTile` 的
  `executeTile` 调用包 try-catch —— 异常不打断计数 → 任务**不悬挂**
- 退役时异常从 BatchState 转移到 `HandleState.batchExceptionPtr`
- `JobHandle::Complete()` 全部 8 个退出点在等退役后 `std::rethrow_exception`
  （rethrow 一次后置 null，防重复抛）
- inline/同步路径（`RunSyncJob`）与快速路径（`FastPath`）同协议 —— 此前
  noexcept 下小 job 直跑回调异常会 std::terminate 进程崩溃（已修）
- C# 路径不受影响：托管侧 `NativeJobCore.cs` 自有 try-catch 记录
  （`RecordJobException`），异常不跨边界逃逸 → **C++ 与 C# 两层异常互不重复**
- `HandleStateView`（C#）只读前 8 字节 → ABI 安全（已实测 C# 无回归）

### 性能零影响（决定性 A/B）

同分钟交替构建/测量（带 vs 不带异常协议 DLL）：

| | 带异常协议 (`aba667b`) | 不带 (`59c0f55`) |
|---|---|---|
| GridSearch Build p50 | 0.84-0.90 | 0.81-0.91 |
| GridSearch Query p50 | 0.64-0.77 | 0.63-0.69 |

差异 <0.02ms = 噪声。原因：x64 MSVC table-based SEH，try-catch 无异常路径
零指令开销；历史 0.58 是更安静机器时段，非回归。

### WhenAll/WhenAny（讨论后未实现 WhenAny）

- `JobHandle::CombineDependencies` = 现有 WhenAll（计数 + 全部完成才完成，
  合成 state 持有依赖引用，RecycleState 释放）
- **WhenAny 暂不实现**（用户决定）：语义复杂（任一完成即完成 + CAS guard
  恰一次 CompleteState + 引用对称），当前无使用场景；如需再加。
