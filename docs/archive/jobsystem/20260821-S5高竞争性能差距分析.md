> 状态：**已解决/追平 + 方差分析完成**。Native S5 中位数 ~3.1-4.3ms，追平 Misaki/TPool；
> ±24-60% 波动来自 OS 调度抖动（workerSpread max ~5.1ms），与 TPool 同级，非 Native 独有问题。
> 统一 worker 标准后确认：之前的"Native 落后 40%"是**基准不对称**（对手满核 PC vs EntJoy 留核 PC-1）。

## 二、基准统一（消除不对称）

### 问题发现
原始基准中 EntJoy 用 `ProcessorCount-1`（15核），对手用 `ProcessorCount`（16核）。
对 S5 纯计算场景，1 核差距 ≈ 6–7% 吞吐损失，放大后掩盖真实水平。

### 修复
`tools\JobLibsBenchmark/Program.cs` 引入统一 worker 标准：

```csharp
// 统一对比标准：所有库共用同一 worker 数（默认 PC-1）
_workerCount = Math.Max(1, Environment.ProcessorCount - 1);
var wEnv = Environment.GetEnvironmentVariable("ENTJOY_BENCH_WORKERS");
if (int.TryParse(wEnv, out var wv) && wv >= 1 && wv <= Environment.ProcessorCount) _workerCount = wv;
int wc = _workerCount;

// Managed/Native/ZeroAlloc/Misaki/PTP 全部用 wc
// TPL(ParFor/TPool) 通过 ThreadPool.SetMaxThreads(wc) 限制
```

- 默认 `wc = PC-1`（尊重主线程留核设计）
- `ENTJOY_BENCH_WORKERS=16` 可覆盖做满核诊断
- 统计改为**9轮取中位数**（`StatsOf` 替代 `MinOf`），输出 `median ± spread%`

### 验证
统一16→15核后，ZeroAlloc 从 3.200 涨到 3.939（少1核掉20%），证实对手原先是满核白占便宜。

## 五、Misaki 架构对比（源码级）

读完 Misaki `JobScheduler.cs` / `WorkerThread.cs` / `JobExecutor.cs` 源码后确认：

| 层 | Misaki | Native | 差异 |
|---|---|---|---|
| 唤醒 | `SemaphoreSlim.Release(N)` 精确唤醒 N 个 | `workEpoch.notify_all()` 广播全部 | Misaki 无惊群 |
| 执行路径 | `Interlocked.Add` → `job.Execute(i)` **2 层** | `fetch_add` → 5层回调 → managed callback | Native 3x 调用深度 |
| Wait | 纯自旋 `SpinWait.SpinOnce(-1)` | assist + spin + condvar | Native 有阻塞路径 |
| 数据结构 | `JobRanges`（3个int struct）| `BatchState`（30+ atomic）| Native 生命周期复杂 |

**但尝试对齐 Misaki 架构（执行路径直调）反而回归**——说明 Native 的5层路径虽然"重"，但经过 JIT/编译器优化后已经和2层路径等效。真正的差距在 OS 调度，不在代码路径深度。

### 精确唤醒（已合入，S5 场景无效但代码正确）

`NativeWorkerPool.cpp` 改动：worker park 在 per-worker `wakeFlag`（`wakeFlag.wait(0)`），Submit 只唤醒收到 work 的 worker（`SelectiveWake`），替代全量广播。Stop 仍用 `WakeAllWorkers()` 广播。

```cpp
// 之前：广播唤醒全部
workEpoch.fetch_add(1, std::memory_order_release);
workEpoch.notify_all();

// 现在：精确唤醒收到 work 的 worker
void SelectiveWake(const std::vector<uint32_t>& wakeCounts) noexcept
{
    for (uint32_t i = 0; i < wakeCounts.size(); ++i)
        if (wakeCounts[i] != 0)
            workers[i]->wakeFlag.notify_all();
}
```

S5 场景无效（390 items /15 workers = 所有 worker 都有活），但对低并行度场景（S2、小 batch）有帮助。

### Relaxed TrySteal（已合入，S5 方差↓2.5x）—— 被动窃取的真正优化

**根因（读 Misaki/TPL 后确认）**：S5 里 Submit round-robin 给所有 worker 置 `wakeFlag=1` + 本地队列。原版 `TrySteal` 跳过 wakeFlag victim，导致快 worker **无法偷 OS 延迟慢 worker 的积压 job**——慢 worker 的 job 干等，整批卡到 OS 唤醒它。

**修复**：`TrySteal` 只跳过 `draining`（owner 正在消费），不再跳过 `wakeFlag`（允许偷 OS 延迟 worker 的 job），保留双检 + 归还防竞态。

```cpp
// 之前：跳过 draining || wakeFlag（快 worker 偷不到 OS 延迟 worker 的 job）
const uint32_t protecting = victim.draining.load(acquire) | victim.wakeFlag.load(acquire);
if (protecting != 0) continue;

// 之后：只跳过 draining（允许偷 OS 延迟 worker 的积压 job）
if (victim.draining.load(std::memory_order_acquire) != 0) continue;
// 双检：pop 后 victim 若已开始 drain → 归还其环
```

**效果（timing 对比）**：

| 指标 | 原始（保护 wakeFlag）| Relaxed TrySteal | 变化 |
|---|---|---|---|
| **S5 方差** | ±60% | **±24%** | **↓2.5x** 🎯 |
| workerSpread max | 5285μs | **5149μs** | 略降 |
| parkWake | 934 | **688** | ↓26% |
| S3 依赖链正确性 | ✅ | ✅ | 无回归 |

**这是正确方向的优化**：在 `DrainAvailableWork` 内优化被动窃取，让事件驱动的窃取真正有效，而非主动扫描（后者已证伪）。

### 已排除（全部回滚）

| 尝试 | 结果 | 原因 |
|---|---|---|
| 静态15 tiles（tile 数=worker 数）| 5.906ms（更差）| 大 tile L1 cache 爆炸 |
| BatchStorage 共享池 | ±59%（波动反弹）| mutex 竞争比堆分配更差 |
| Managed batch runner | 6.188ms（更差）| 执行路径优化方向错误 |
| 执行路径直调（5→3层）| 4.407ms（回归35%）| 丢失 prefetch / 调用链优化依赖原路径 |
| **主动窃取（spin-window 扫描）**| workerSpread P50 差4.5x | 自旋窗内扫描空转，负收益 |

## 九、已知局限（不再优化）

| 局限 | 原因 | 影响 |
|---|---|---|
| ±24–60% 波动（Native S5 3.1–4.5ms）| OS 调度抖动（workerSpread max ~5.1ms）| 所有库同级（TPool/Misaki 波动重叠）|

## 十、NativeTranspiler C++/ISPC 对比基准（本 session 落地）

`tools/JobLibsBenchmark` 接入 NativeTranspiler，新增 Cpp/Ispc 两列，与托管列同场景对比。核心结论：**transpile 是唯一可复现的大杠杆（3-10x）**。

### 改动的文件
| 文件 | 内容 |
|---|---|
| `JobLibsBenchmark.csproj` | 自包含 NativeTranspiler 集成（引用源生成器 + NativeCompileTask CMake/VS/ISPC 构建），无手动同步 bin |
| `NativeBenchJobs.cs`（新建）| 14 个 `[NativeTranspile]` job（S1/S2/S3/S5 × Cpp/Ispc），字段 `NativeArray<T>`（非托管）|
| `Program.cs` | 新增 Cpp/Ispc 列 + 10 个测量函数 + 汇总表（9 实现自动打印）|

### 坑（已写进 NativeBenchJobs.cs 注释）
1. `Execute` 必须用块体 `{}`（非 `=>`，源生成器依赖方法体）
2. 字段必须 `NativeArray<int>`（非托管），不能 `int[]`
3. ISPC 不支持 64 位 long → S5 重算用 `int` 累加

### 实测结果（transpiled vs 托管回调，3-10x）
| 场景 | Native(C#托管回调) | Cpp(transpiled) | Ispc(transpiled) | 提升 |
|---|---|---|---|---|
| S1 加法 | ~0.2-0.6 | ~0.03-0.09 | ~0.03-0.08 | ~5-8x |
| S2 空任务 | ~0.3-0.6 | ~0.18-0.28 | ~0.05-0.2 | ~2-10x |
| S3 依赖链 | ~0.8-1.5 | ~0.08-0.6 | ~0.07-0.15 | ~3-14x |
| S5 高竞争 | ~3.3-4.7 | ~0.55-1.0 | ~0.47-0.56 | **~6x** |

**根因**：transpiled 绑定用 `Get_XXX_Execute_AdapterPtr()` 给原生调度器一个**原生函数指针**，原生→原生直跑，**完全绕开 managed/native 跨边界回调 + C# Execute 的 JIT 标量执行**。托管回调路径每个 tile 都要 GCHandle 解引用 + delegate 跨边界 + JIT 跑内循环，这是差距来源。

### 为什么是"唯一大杠杆"
- 托管 C# job 只要保留 `Execute` 走 JIT，就消不掉跨边界回调 + 标量执行（物理约束）
- 转原生（Cpp -O3 / ISPC AVX2 向量化）拿到的是**向量化 + 零跨边界**，3-10x

## 十一、tile/PW 自适应调查（结论：噪声，已回滚）
