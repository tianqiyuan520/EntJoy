# MPMC vs Chase-Lev Deque 深度分析（2026-08-21）

> 本文档分析为什么 Unity Job System 选择工作窃取（Chase-Lev Deque）而非 MPMC 环形队列作为核心调度结构。

---

## 一、Unity 的设计哲学

Unity 官方文档没有明确说明其 Job System 使用了 Chase-Lev Deque，但可以确认：

1. **工作窃取是核心调度策略**：每个 Worker 有自己的任务队列，空闲时从其他 Worker 窃取任务
2. **原子操作是关键特征**：官方明确指出 IJobParallelFor 使用原子操作执行工作窃取
3. **Chase-Lev 是事实标准**：Rust crossbeam、Intel TBB 等高性能并发库均采用

---

## 二、MPMC vs Chase-Lev 核心区别

### 2.1 调度模型

| 维度 | MPMC 环形队列 | Chase-Lev Deque |
|---|---|---|
| **模型** | 推送式（集中竞争） | 拉取式（分布式） |
| **数据结构** | 全局共享队列 | 每个 Worker 一个本地队列 |
| **竞争点** | 所有线程竞争同一个队列 | 仅窃取时竞争（低频） |

### 2.2 缓存局部性

**MPMC**：
```
Worker 0 → 全局队列（L3 cache）→ 竞争 CAS → 取任务
Worker 1 → 全局队列（L3 cache）→ 竞争 CAS → 取任务
Worker 2 → 全局队列（L3 cache）→ 竞争 CAS → 取任务
```
所有 Worker 访问同一个全局队列，缓存行在不同核心间颠簸。

**Chase-Lev**：
```
Worker 0 → 本地 Deque（L1 cache）→ 无竞争 Pop
Worker 1 → 本地 Deque（L1 cache）→ 无竞争 Pop
Worker 2 → 本地 Deque（L1 cache）→ 无竞争 Pop
空闲时 → 窃取其他 Worker（CAS，低频）
```
大多数操作在本地 L1/L2 cache 完成，仅窃取时才跨核。

### 2.3 可扩展性

**MPMC**：
- 核心数 ↑ → 竞争 ↑ → CAS 重试 ↑ → 性能 ↓
- 16 核时竞争已经很明显

**Chase-Lev**：
- 核心数 ↑ → 本地操作占比 ↑ → 竞争分散 → 性能 ↑
- 理论上线程越多优势越明显

### 2.4 FIFI vs LIFO+FIFO

**MPMC**：严格 FIFO
- 所有任务按提交顺序执行
- 无法利用时间局部性

**Chase-Lev**：LIFO（本地）+ FIFO（窃取）
- 本地执行用 LIFO（后进先出）：利用缓存时间局部性
- 窃取用 FIFO（先进先出）：窃取最老的任务，减少竞争

---

## 三、MPMC 的固有局限

### 3.1 容量固定
环形缓冲区通常有界。如果任务生产速度超过消费速度，队列会满，导致生产者阻塞。对于任务数量动态变化极大的游戏引擎，这是难以接受的限制。

### 3.2 FIFO 顺序限制
MPMC 是严格的 FIFO 结构。而工作窃取使用双端队列（Deque），允许线程从队首（LIFO）处理自己的任务，从队尾（FIFO）窃取任务，这种机制能更好地利用缓存并减少竞争。

### 3.3 全局竞争
MPMC 为了实现无锁，依赖昂贵的 CAS 操作。在高并发下，线程们争抢同一个队列，导致大量 CAS 重试和缓存失效，形成性能瓶颈。

---

## 四、工作窃取的优势

### 4.1 缓存局部性
每个线程主要操作自己的队列，数据和任务都能很好地留存在 CPU 核心缓存中。

### 4.2 避免全局竞争
窃取是低频事件。大多数时候线程都在无竞争地操作自己的本地队列，大大降低了同步开销。

### 4.3 可扩展性
工作窃取算法被设计为高度可扩展的，理论上线程越多优势越明显，因为竞争被分散化。

---

## 五、MPMC 的适用场景

MPMC 队列并非一无是处，它在以下场景仍有价值：

1. **数据容器**：Unity 的 `NativeQueue<T>` 就是 MPMC，用于 Job 之间安全传递数据
2. **简单生产者-消费者**：单生产者多消费者场景
3. **低并发**：核心数少时竞争不明显

但在**任务调度器核心**这个场景下，Chase-Lev 是更好的选择。

## 六、对 EntJoy 的启示

### 6.1 当前架构的问题

```
当前: 全局 MPMC 队列 + nextTile.fetch_add(4) + 15 worker 竞争同一个原子
     ↓
每个 batch 的 240 tiles 都在同一个"战场"上竞争
     ↓
原子争用 = S5 方差的主要来源之一
```

### 6.2 Chase-Lev 的改进

```
新架构: 每个 Worker 一个本地 Deque + 全局队列仅作入口
     ↓
Worker 先处理自己 Deque 里的任务（无竞争）
     ↓
空闲时才窃取其他 Worker 的任务（低频 CAS）
     ↓
竞争分散化，缓存友好
```

### 6.3 预期收益

| 场景 | 预期改善 |
|---|---|
| S5 高竞争 | 持平或略优（均匀负载下窃取少）|
| GridSearch | 显著改善（不规则负载下窃取动态均衡）|
| 高核心数扩展 | 显著改善（竞争分散化）|
| 缓存命中率 | 改善（本地 Deque 操作在 L1/L2 内）|

---

## 七、结论

Unity Job System 选择工作窃取（Chase-Lev Deque）而非 MPMC 环形队列，是一个经过深思熟虑的架构决策：

1. **为了性能**：缓存局部性更好、竞争更少、扩展性更强
2. **为了灵活性**：避免有界队列带来的阻塞风险和 FIFO 顺序的限制
3. **为了分工**：将 MPMC 队列作为专用的线程安全容器，而不是通用的任务调度器

对于 EntJoy，重构为 Chase-Lev Deque 是迈向更高性能上限的正确方向。
