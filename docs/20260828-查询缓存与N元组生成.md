# 2026-08-28 查询缓存共享与 N 元组查询生成器

> 本次改动覆盖：EntityQuery 共享注册表（S20 查询缓存部分）、Entity Group 反向索引、
> N 元组查询 SourceGenerator（`world.Query<T0..Tn>()`）、SystemAPI 移除、09_ECS 目录整理。

## 一、背景

原 `World.CreateEntityQuery` 每次调用都 `new EntityQuery` 并全量扫描所有 Archetype（`EntityQuery.cs` 构造即 `Refresh()`），
相同规则的查询被重复构造 + 重复扫描。`world.Query<T0, T1>()` 固定 2 组件上限，3+ 组件查询编译不过。

## 二、EntityQuery 共享注册表（S20 查询缓存）

### 设计

| 组件 | 说明 |
|---|---|
| `QueryKey` | 规则指纹：All/Any/None/AllEnabled 的 ComponentType.Id 序列 + SharedFilter。**排序归一**（`Array.Sort`）——匹配语义与顺序无关，`WithAll<A,B>` 与 `WithAll<B,A>` 共享同一实例 |
| `World.GetOrCreateEntityQuery` | 按 `QueryKey` 查表共享实例，O(1) 命中，避免重复构造 + 全量重扫 |
| `EntityQuery.RefreshIncremental` | 两级判定：Archetype 集合未变化（`archCount == _scannedArchetypeCount`）→ 复用签名匹配集合，只重收 chunk；Archetype 增删 → 全量重扫 |
| 惰性刷新 | 访问时版本检查（`StructuralVersion` 对比），结构变更路径零额外成本，无需 EntityManager→World 通知 |

### 基准（09_ECS/Benchmarks/EntityQueryCacheBenchmark.cs）

5 万实体 / 4 Archetype / 200 迭代：

| 指标 | 结果 |
|---|---|
| 共享查表 vs 重复构造 | 0.0009 ms vs 0.0035 ms = **4.12x 提速** |
| 增量刷新正确性 | delta 10000 = 预期 10000 OK |
| 增量刷新耗时 | 0.0454 ms/iter（100 新实体 + 查询） |

## 三、Entity Group 反向索引

### 设计

- **结构**：`Archetype → List<EntityQuery>`（Archetype 匹配哪些查询）
- **查询路径**：`world.GetGroupsOf(entity)` = 实体定位 Archetype（O(1)，复用 `EntityIndexInWorld`）+ Archetype→查询查表
- **惰性构建**：`_groupIndexVersion` 聚合版本（查询数 + 各查询 StructuralVersion 之和）判脏，变化才重建——结构变更路径零额外成本
- **API**：返回 `IReadOnlyList<EntityQuery>`（只读视图，零拷贝）

### 实测（基准第 3 部分）

| 验证点 | 结果 |
|---|---|
| 实体 #0（[P,V]）匹配 | qPV + qP，不含 qH ✅ |
| AddComponent\<Health\> 后 | 含 qH ✅ |
| RemoveComponent\<Velocity\> 后 | 不含 qPV ✅ |
| GetGroupsOf 性能 | **0.08 us/iter** |

## 四、N 元组查询生成器（QueryTupleSourceGenerator）

### 需求

`world.Query<Position, Velocity, Health>()`（3+ 组件）原编译不过——`QueryEnumerable<T0,T1>` 固定 2 上限。

### 实现（A 方案：生成器生成完整枚举器）

| 步骤 | 说明 |
|---|---|
| `TempBuffer` public 化 | 生成器枚举器位图缓冲（用户程序集访问） |
| `QueryTupleSourceGenerator` | 扫描 `world.Query<T0..Tn>()` 调用点（N≥3），为每个唯一元组组合生成 `QueryEnumerable`/`QueryEnumerator`/`EntityQueryResult` N 元组版 + `QueryTupleWorldExtensions` 扩展方法 |
| `ECSSourceGenerator` 注册 | 复合生成器登记新子生成器 |

### 关键坑（调试记录）

1. **增量生成器鸡生蛋**：首次编译时 N 元组重载尚不存在，语义模型 `GetSymbolInfo` 找不到方法符号 → 不能依赖方法解析，改为语法级提取泛型实参 + `GetTypeInfo` 解析类型实参
2. **partial 跨程序集不合并**：生成器在用户程序集无法给库的 `World` 注入成员 → 用**扩展方法**（`this World world`）
3. **N≥3 限定**：2 元组库内已有 `QueryEnumerable<T0,T1>`，生成会重复定义冲突
4. **`global::` 前缀**：`ToDisplayString(FullyQualifiedFormat)` 输出 `global::EntJoy.ECS.World`，符号匹配需归一前缀
5. **SystemAPI 不能做扩展接收者**：静态类不能用作 `this` 参数 → 后随 SystemAPI 移除一并解决

### Config 收编（防硬编码/改名）

`Config.cs` 新增：`QueryMethod`/`WorldFullName`/`WorldTypeName`/`MinTupleArity`。
`GetTuples` 用符号匹配：`GetTypeInfo(ma.Expression)` 解析接收者类型 → 归一 `global::` → 必须等于 `Config.WorldFullName` 才生成。
变量名随意（world/w/myWorld）均可识别；改名/误用不误生成。

### 使用效果

```csharp
foreach (var r in world.Query<Position, Velocity, Health>())
{
    r.Comp0.X += r.Comp1.X * 0.016f;
    r.Comp2.Current -= 0.1f;  // Comp0/1/2 强类型
}
```

## 八、遗留与后续

1. **`QueryBuilder.WithAll` 仅到 2 泛型**：`WithAll<A,B,C>()` 编译不过，需链式。高价值项——影响所有上层 API（Query/QueryChunks/EntityQuery/共享查询）
2. **`World.QueryChunks` 仅 2 泛型**：chunk 级遍历缺 N 元组（可复用 QueryTuple 生成器模式）
3. **`QuerySelection.WithEnabled` 2 上限**：低频便利链
4. **SystemAPI N 元组**：随移除不再需要
5. `QueryTupleTests` 可补 N=4 用例验证更大 N 健壮性
