# Unity 集成基准：实现、问题与分析（2026-08-23）

> Unity 版本：6000.3.2f1 | 环境：Windows 11 x64，16 核（PC-1 = 15 Workers），AVX2
> 基于：`tools/JobLibsBenchmark` 的 S1-S6 场景，三路对比（EntJoy Managed / Native / Unity Burst）

## 一、实现方案

### 1.1 架构：EntJoy 源码移植（非 DLL 引用）

因 EntJoy 源码为 net8.0，无法直接引用进 Unity（netstandard2.1）。采用**源码复制 + 兼容修复**方案：

```

├── EntJoy.Port/                    ← EntJoy.Collections + Jobs 源码副本（25 个 .cs）
│   ├── EntJoy.Port.asmdef          ← asmdef（AllowUnsafe=true）
│   ├── Polyfills.cs                ← 兼容垫片
│   └── *.cs                        ← 源码副本（含 7 处内联修复）
├── UnityBenchJobs.cs               ← Job 定义（EntJoy 8 struct + Unity 6 struct + S6 扩展）
├── UnityJobBench.cs                ← 基准引擎 + Editor 菜单 + Play 模式 Runner
├── UnityJobBenchBootstrap.cs       ← 调度器生命周期管理
├── Generated/
│   └── NativeTranspiler.Bindings.g.cs  ← NativeTranspiler 离线绑定（dump 落盘）
└── README.md
```

## 二、遇到的问题与修复

### 2.1 BitOperations.Log2 polyfill 错误（崩溃根因）

**现象**：`NativeArray<int>(Persistent)` 构造时 `MemClear` 传入 NULL 指针 → NullReferenceException

**根因**：Polyfills.cs 的 `BitOperations.Log2` 用 `<=` + 左移（`value <<= 16`），算出错误的 log2 值（如 `Log2(5)` 返回 31 而非 2），导致 `PersistentAllocator.SizeToClass` 计算错误的 size-class → 分配失败返回 NULL。

**修复**：改为标准二分找最高位（`& mask != 0` + `>>=`）：
```csharp
if ((value & 0xFFFF0000u) != 0) { n += 16; value >>= 16; }
if ((value & 0x0000FF00u) != 0) { n += 8;  value >>= 8; }
...
```

### 2.2 NativeDll.dll 版本不匹配

**现象**：`EntryPointNotFoundException: Export not found: JobSystem_GetStatsSize`

**根因**：Unity 进程加载了旧版 `NativeDll.dll`（`LoadLibrary` 对已加载模块返回缓存句柄，覆盖文件不生效）。

**修复**：完全重启 Unity Editor 进程。

### 2.3 ISPC S6 在 Unity 里慢 10 倍（已定位并修复）

**现象**：S6 ISPC 在 Unity = 56.2ms，tools = 5.5ms（10 倍差距）

**排查过程**：
1. 诊断直调 ISPC 内核 = 55.2ms（单线程，SIMD 正常）→ 内核本身没问题
2. 诊断 Schedule+Complete = 0.977ms（Heavy）→ 调度开销正常
3. NativeJobHandle/JobExtensions 与 tools **完全一致**（0 行差异）→ 移植无问题
4. Native 和 Cpp 在 Unity 里性能一致（53ms vs 53ms）→ Mono 不是主因

**根因**：`Generated/NativeTranspiler.Bindings.g.cs` **缺少 S6 Ctrl job 的绑定**

Unity 侧 bindings 是旧版 dump（8:11 生成），早于 S6 Ctrl job 加入 tools 源码（8:23 修改）。导致 `NativeCtrlCpp` / `NativeCtrlIspc` 在 bindings 中零出现。

`NativeTranspiler.Bindings.g.cs` 的全局命名空间 `JobExtensions` 为 S1-S5 每个 job 生成了专属非泛型重载（如 `Schedule(this NativeHeavyIspc, ...)`），走原生内核。而 S6 缺专属重载 → `.Schedule()` 回落到 `EntJoy.JobSystem.JobExtensions.Schedule<T>` 泛型托管回调 → **纯 C# 逐元素 LCG 标量执行**（56ms ≈ Managed 49ms），而非原生 ISPC 内核。

**修复**（手工补 bindings，与生成器输出等价）：

在 `Generated/NativeTranspiler.Bindings.g.cs` 中补齐 NativeCtrlCpp/NativeCtrlIspc 的完整绑定：
- `NativeExports` 静态字段：`s_NativeCtrl{Cpp,Ispc}_{BatchFunc,BatchFuncPtr,CleanupFunc,CleanupFuncPtr}`
- static ctor 初始化（`Get_NativeCtrl{Cpp,Ispc}_Execute_AdapterPtr()` + cleanup delegate）
- `RegisterJobFieldWriter` 注册
- `DllImport`：`NativeCtrl{Cpp,Ispc}_Execute_Batch` + `Get_NativeCtrl{Cpp,Ispc}_Execute_AdapterPtr`
- `Schedule_NativeCtrl{Cpp,Ispc}(...)` 方法（context 32B：Results_ptr@0 + Results_length@8）
- `WriteJobFields_NativeCtrl{Cpp,Ispc}`
- 全局命名空间 `JobExtensions` 专属重载：`Schedule(this NativeCtrl{Cpp,Ispc}, int, int, JobHandle)` + `Run`

**修复后验证**（2026-08-23 实测）：

| 路径 | 修复前 | 修复后 | 说明 |
|---|---|---|---|
| S6 ISPC tiled (.Schedule()) | 56.2ms | **5.508ms** | ✅ 10x 提升，恢复原生 ISPC |
| S6 Cpp tiled (.Schedule()) | 52.9ms | **41.5ms** | ✅ 恢复原生 C++（但仍慢于 ISPC） |
| 手动原生调度 (ScheduleParallelForBatchRaw) | — | 5.213ms | 与 .Schedule() 一致，证明绑定路由正确 |
| S6 Ispc 直调（单线程） | 55.2ms | 55.2ms | 不变（基准线） |

绑定完整性检查（修复后全绿）：
```
NativeAddCpp     ScheduleNative=True 专属Schedule扩展=True
NativeAddIspc    ScheduleNative=True 专属Schedule扩展=True
NativeHeavyCpp   ScheduleNative=True 专属Schedule扩展=True
NativeHeavyIspc  ScheduleNative=True 专属Schedule扩展=True
NativeCtrlCpp    ScheduleNative=True 专属Schedule扩展=True  ← 修复前为 False
NativeCtrlIspc   ScheduleNative=True 专属Schedule扩展=True  ← 修复前为 False
```

**注意事项**：
- bindings 是 `// <auto-generated/>` 文件，下次跑 `build.ps1` 重新 dump 会覆盖
- tools 侧生成源已含 Ctrl + `[NativeTranspile]`，重 dump 会正确包含 Ctrl
- 手工补的绑定与生成器输出同构，是安全的即时修复

### 2.4 S5 Clang 代数简化

**现象**：Cpp S5 = 0.055ms（比 tools 的 0.049ms 略慢），远快于 ISPC 的 0.552ms

**诊断**：直调 C++ 内核 = 0.014ms（Clang 把 `sum += index * j` 优化为 `index * 499500`，单条 `imul` 指令）

**结论**：Clang `/O2` 做了代数简化，ISPC 不做。S5 是编译器差异，非公平对比。S6 是公平场景。

### submit 内部构成精确定位（可优化部分）

`ChaseLevScheduler::SubmitBatch` 内部（tpw=4 后 15-20μs / 15 workers；tpw=26 时 30-35μs）：
1. **RangeTask 入队**（taskPool.Acquire + PushTaskBackoff）：60 tiles → ~4 tasks（tpw=4），~1-2μs
2. **wakeEpoch.fetch_add + notify_all()**（广播唤醒 15 workers futex）：**~10-15μs（主成本）**

`WorkerLoop` 等待机制（ChaseLevScheduler.cpp L725-753）：
1. 无工作时 spin 256 次（~2-4μs）检查 wakeEpoch
2. Spin 耗尽后 `wakeEpoch.wait(seenStamp)` — 共享 futex park
3. SubmitBatch `notify_all()` → 内核唤醒全部 park 的 worker → 每个 worker 一次上下文切换

**15 workers 唤醒成本分布的推断**：
- futex syscall（1 次通知 15 线程）+ 15 次内核调度 → ~10-15μs
- 15 次用户态上下文切换（worker 从 park 恢复）→ ~15-20μs
- 首次任务提取 + deque 竞争 → ~2-5μs

## 优化方向（正确的方向：加快唤醒，而非降 worker 数）

> ⚠ 之前"workerCap 限制参与 worker 数"的方向有误：降 worker 数会牺牲并行度，
> 对重计算任务（S6 等）反而更慢。真正的优化是**让 15 workers 唤醒更快**。

### per-job 自动 batch（JobCostCache）—— 已按此设计落地（git 6ebda28）

> 本节为落地前设计稿，保留作实现依据；落地结果见 §五-5/6。与原设计的差异：
> ① 加 `kMaxAutoChunk=32k` 安全护栏（原稿无——大 job 塌缩串行回归后补）；
> ② EWMA 无上升阻尼（原稿未提——成本波动场景实测后减掉 4x 升限）；
> ③ Update 用 CAS 循环（原稿为 load→store，有并发丢更新面）。

#### 问题本质

固定 tpw=4 对所有 job 一刀切：light job 需要更少 tiles（4→~1），heavy job 需要更多 tiles（4→~100）。无法同时最优。

**解法**：用 per-job 的**每元素成本 EWMA**，自动求解每 job 的最优 tile 数。
且需 **export flag 控制**：关闭时不记录、不使用 cache，只用 tpw=4 兜底。

#### 核心设计

**1. Export flag（控制 cache）**

```cpp
// Exports.h + JobSystemInternal.h
extern std::atomic<bool> g_jobCostCacheEnabled;  // 默认 false（关闭）

// C# 侧可调：
JOB_API void JobSystem_SetJobCostCacheEnabled(int enabled);
```

- **flag = 0（默认）**：不记录、不使用 → 纯 tpw=4，行为与现状完全一致
- **flag = 1**：启用 → 记录每元素成本 + 自动计算 tile
- **只在明确需要时开启**：用户/应用层决定（避免意外行为变化）

**2. JobCostCache（记录 per-job 每元素成本）**

```cpp
// 固定 256 槽数组（2KB），无锁，funcPtr 哈希碰撞复用
constexpr int kJobSlots = 256;
std::atomic<uint64_t> g_jobPerElemEwmaNs[kJobSlots];  // 每元素 ns（Q22 定点）
std::atomic<uint32_t> g_jobSlotHash[kJobSlots];        // funcPtr hash 校验

// 热路径开销：<3ns（1 次 AND + 1 次数组读，对 16μs 调度的 0.02%）
static double GetPerElemCost(uint32_t funcHash) noexcept {
    int slot = funcHash & (kJobSlots - 1);
    return (g_jobSlotHash[slot].load(relaxed) == funcHash)
        ? g_jobPerElemEwmaNs[slot].load(relaxed) / Q22_SCALE : 0.0;
}

// worker 执行 tile 完成后反推更新：
static void UpdatePerElemCost(uint32_t funcHash, double perElemNs) noexcept {
    int slot = funcHash & (kJobSlots - 1);
    g_jobSlotHash[slot].store(funcHash, relaxed);
    auto old = g_jobPerElemEwmaNs[slot].load(relaxed);
    auto new_ = static_cast<uint64_t>(perElemNs * Q22_SCALE);
    g_jobPerElemEwmaNs[slot].store(old + ((new_ - old) * 3) >> 2, relaxed);  // α=0.75
}
```

- **记录时机**：仅在 `g_jobCostCacheEnabled == true` 时才调用 Update
- **关闭时**：Get 返回 0（冷启动），Update 不调用 → 零开销
- **容量**：256 种 job，碰撞复用重学，无正确性风险

**3. 自动 tile 计算（ResolveChunkSize 增强）**

```cpp
int ResolveChunkSize(int length, int requestedChunk, uint32_t funcHash)
{
    if (length <= 0) return 1;
    if (requestedChunk > 0) return requestedChunk;
    int wc = std::max(1, g_numThreads);

    // 自动 batch：仅在 g_jobCostCacheEnabled 且有数据时
    if (g_jobCostCacheEnabled.load(relaxed))
    {
        double perElemNs = GetPerElemCost(funcHash);
        if (perElemNs > 0)
        {
            double totalUs = length * perElemNs / 1000.0;
            // 目标每 tile 150μs（调度 ~16μs → 占比 ~10%）
            constexpr double kTargetTileUs = 150.0;
            constexpr double kMinTileUs = 30.0;    // 防调度浪费
            constexpr int kMaxAdaptiveTpw = 16;     // tiles 上限 = workers×16
            constexpr int kMinAdaptiveTpw = 1;      // 最轻 job 近乎串行

            double targetTilesD = std::clamp(totalUs / kTargetTileUs, 1.0,
                                             (double)wc * kMaxAdaptiveTpw);
            int targetTiles = (int)targetTilesD;
            if (targetTiles > 1 && totalUs / targetTiles < kMinTileUs)
                targetTiles = (int)std::max(1.0, totalUs / kMinTileUs);
            return std::max(1, (length + targetTiles - 1) / targetTiles);
        }
    }
    // 冷启动 / flag 关闭 → tpw=4 兜底（现状）
    return std::max(1, (length + wc * g_configuredTilesPerWorker - 1)
                       / (wc * g_configuredTilesPerWorker));
}
```

**4. 调用链完整流程**

```
BatchState 完成后（worker 侧）：
  → perElemNs = rangeExecTimeNs / rangeLength
  → if (g_jobCostCacheEnabled) UpdatePerElemCost(funcHash, perElemNs)

下次同类型 job 调度时：
  → ResolveChunkSize(length, 0, funcHash)
    → GetPerElemCost(funcHash) = 非 0（已学习）
    → totalUs = length × perElemNs
    → tiles = clamp(totalUs / 150μs, 1, workers×16)
    → chunk = length / tiles

首次调度（冷启动）：
  → GetPerElemCost(funcHash) = 0（无数据）
  → 走 tpw=4 兜底（60 tiles / 15 workers）
```

#### 优化效果预期

| Job 类型 | perElem | 自动 tiles | worker 数 | 调度 p50 | vs tpw=4 |
|---|---|---|---|---|---|
| 超轻（S5，0.05ns） | total≈5μs | ~4 | 4 | ~5μs | **0.024→0.013ms** |
| 中（S1，~30ns） | total≈30μs | ~15 | 15 | ~16μs | 0.024→0.03ms |
| 重（S6，~0.4μs） | total≈40ms | ~240 | 15 | ~16μs | 40.9ms（维持） |
| 冷启动 | — | 60（tpw=4） | 15 | 16.5μs | 同现状 |

#### 为什么能生效（连锁反应）

```
自适应 tiles ↓
  → worker 数 = min(tiles, 15) 自动跟着降
  → notify_all 广播数 ↓
  → 唤醒成本 ↓（16.5μs → 5μs for 4 workers）
```

这就是"一个改动拿到两份收益"：**tile 粒度优化 + 唤醒成本降低同时实现**。

#### 安全设计

| 风险 | 应对 |
|---|---|
| cache 影响性能 | **flag 默认关闭**，不记录、不使用 → 零开销 |
| 首轮无数据 | 走 tpw=4 兜底，与现状一致 |
| 碰撞导致数据错误 | 256 槽碰撞复用 → EWMA 重学，无正确性风险 |
| job 成本变化（运行时） | EWMA 跟踪，滞后几轮自动调整 |
| 重任务误判为轻 | perElem 足以区分：S5=0.05ns vs S6=0.4μs，差 8000 倍 |

#### 诚实评估

| 收益场景 | 预期 | 说明 |
|---|---|---|
| S5 轻任务（first-run 后） | 0.024→0.013ms（2 倍） | 多次调度建立 EWMA 后 |

## 五、已知问题与后续

1. **S5 代数简化**：Cpp S5 是 Clang 编译器差异（自动简化），非公平对比。S6 是唯一公平的重计算场景。
2. **IL2CPP 兼容**：已完成 AOT 兼容修复（反射→静态泛型、UnmanagedCallersOnly→delegate、ModuleInitializer→显式调用），待 Windows Standalone IL2CPP 构建验证。
3. **✅ tpw=4 已落地**（2026-08-23）：`TilesPerWorker` 26→4，S5 Cpp tiled 0.050→~0.024ms（2 倍），S6 略慢 10%（40.9ms，重任务可接受）。与 ECS kTargetTilesPerWorker=4 一致。
4. **✅ 调度开销 profiling 定位**（2026-08-23）：tpw=4 后 dispatch p50 ~16.5μs，连续调度可低至 3-7μs（worker 未 park）。
5. **✅ per-job 自动 batch（JobCostCache + export flag）已落地**（git 6ebda28）：per-job 每元素成本 EWMA 自动求解 tile 数。**flag 默认开启**；关闭走纯 tpw=4（`JobCostCacheEnabled=false` 或 `ENTJOY_JOB_COST_CACHE=0`）。实测 S5 0.024→**0.008ms**（超原目标 0.013）。关键点：
   - 256 槽无锁 EWMA（Q22 + FNV-1a hash，碰撞重学，CAS 防并发丢更新）
   - `kMaxAutoChunk=32k` 元素护栏：防大 job 塌缩成串行巨型 tile（曾致 S3 0.164 回归，已修复）
   - 双向 α=0.75 无上升阻尼：成本波动（10↔10000 次循环）1-2 轮跟随
   - **serialUs 校正**：`tiles = clamp(serialUs/150μs, 1, wc×16)`，`serialUs = N×perElem_wall×wc`
     （perElem 是并行 wall 稀释成本；不乘 wc 会把中间量级 job 塌成 4-15 个巨型 tile →
     GridSearch 实测 BuildCore 0.57→1.09ms / Query 0.67→2.12ms 2-3x 退化，修正后 0.70/0.81ms 持平）
6. **✅ 自适应自旋已落地**（git 6ebda28）：WorkerLoop 执行任务后拉满 `kSpinMax=4096`，空转指数退火（÷2 下限 64），全局在飞用 `kSpinBusy=8192`。与 JobCostCache 协同后：S2 0.007 / S3 0.053 / S5 0.008ms（tpw=4 基线 0.026/0.087/0.024）。
7. **✅ 旧路径 NativeWorkerPool 已移除**（git 6ebda28）：Chase-Lev 唯一调度路径。删双路径分叉（g_useWorkStealing）与旧执行/退役死代码，净删 ~650 行；WorkerSnapshot 迁独立头。
8. **ISPC 代数简化**：ISPC 不做代数简化（S5 Ispc=0.606ms vs Cpp=0.050ms）。可考虑在 transpiler 层面对简单循环做代数预处理。

### 6.3 S5 Ispc 已知环境差异（不修）

- tools/.NET：0.557ms；Unity 编辑器/IL2CPP：~1.6ms；Mono 导出（旧 DLL，无法复现路径）：0.525ms。
