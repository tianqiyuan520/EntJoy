# 基准测量方法论与调度开销分析

> 配套 [docs/03](03-NativeAdapter-Query开销分析与调度优化.md)（Query 开销分析与调度优化）。
> 本文档回答三个问题：怎么测才可信、调度开销分布在哪、还有多少可挤的空间。

---

## 1. 测量方法论（降低噪声）

### 1.1 噪声源

| 噪声 | 量级 | 性质 |
|---|---|---|
| 运行间漂移（turbo boost / 温度 / 后台进程） | ±0.05ms | 不可消除，只能稀释 |
| 帧内尾部（p95-p50） | ~0.14ms | 带宽争用 + 系统抖动，inherent |
| 首帧冷启动（分配器/worker 冷） | 显著 | 用 warmup 吸收 |

### 1.2 已内置的降噪手段（TestGridSearch.cs）

| 手段 | 说明 |
|---|---|
| warmup 帧（`ENTJOY_BENCH_WARMUP`，默认 5） | 测速前先跑 N 帧，让 CPU/分配器/worker 热起来 |
| 采样帧数（`ENTJOY_BENCH_FRAMES`，默认 100） | 样本量决定 p50/p95/p99 可信度 |
| **中位数优先** | p50 比 avg 抗 outliers（`PrintSummary` 统一输出） |
| STEADY 阶段 | 暖路径复用缓冲（`UpdatePositions`），隔离冷分配方差 |
| sleep 模式（`ENTJOY_BENCH_SLEEP`=1） | 每帧插 16ms，模拟真实游戏帧间隙 |

### 1.3 不建议的降噪手段

**锁进程优先级 / 核亲和**：Unity 不这么做（见 §3）。仅可作**临时**测量手段（对比数字时手动用），
**绝不进框架/运行时**——游戏跑在用户机器上，抢占优先级会卡别的进程，硬编码亲和会伤害异构 CPU。

### 1.4 env 变量全清单（8 个，全部测试/诊断门控，零生产路径）

| 变量 | 位置 | 作用 |
|---|---|---|
| `ENTJOY_BENCH_WARMUP` | TestGridSearch.cs:82 | 预热帧数 |
| `ENTJOY_BENCH_FRAMES` | TestGridSearch.cs:83 | 采样帧数 |
| `ENTJOY_BENCH_SLEEP` | TestGridSearch.cs:84 | 16ms 帧间隙模式 |
| `ENTJOY_PERSISTENT_POOL_STATS` | TestGridSearch.cs:187 | 分配器命中率诊断 |
| `ENTJOY_GUIDED_TILES` | NativeJobScheduler.cs:755 | guided 开关 |
| `ENTJOY_GUIDED_K` | NativeJobScheduler.cs:758 | guided tiles/worker |
| `ENTJOY_GUIDED_FLOOR` | NativeJobScheduler.cs:761 | guided 最小 tile |
| `ENTJOY_QUERY_BATCH` | （历史遗留，doc 提到但代码已无） | QueryBatchSize 现硬编码 0 |

每个都是独立调参维度，刻意不用配置文件/命令行参数，为的是 PowerShell 里 `$env:X=Y; dotnet run`
快速 A/B 扫参、免重编译。

## 2. 调度开销分布（post-guided）

### 2.1 wake 成本两个区间（关键区分）

| 场景 | 成本 | 结论 |
|---|---|---|
| **紧循环**（本基准，连续 query） | 尾宽主因是 **per-query 代价方差 + 带宽**，非 wake | keep-warm spin 实验负结果（见 `keep-warm-spin-negative-result.md`） |
| **16ms 帧间隙**（`ENTJOY_BENCH_SLEEP`=1） | +0.27ms 全唤醒（worker park→wake 上下文切换） | 若走真实帧间隔会显现 |

→ **调度器自旋不是解药**：紧循环下 worker 本来就在忙，帧间隙下自旋又回归（已被还原）。

### 2.2 post-guided 剩余分布（估算，p50 ~583μs）

| 项 | 量级 | 占比 | 可挤性 |
|---|---|---|---|
| job 执行（内存受限 gather） | ~550μs | ~94% | **地板**，调度不可削 |
| submit→first worker + wake | 9~28μs | 2~5% | worker 唤醒是上下文切换物理下限（~10μs），prewake 已做，边际 |
| tile-claim（原子 fetch_add） | ~10-20μs | 2~3% | guided 已减认领数，余量小 |
| Schedule + Complete 两次 P/Invoke | ~1μs | <0.2% | 可合并，收益可忽略 |

**结论**：框架调度侧已到收益递减区。剩余大杠杆在**数据布局**（§3/§4）。

### 2.3 进一步选项（按收益排序）

| 方案 | 预期 | 约束 |
|---|---|---|
| **GridSearch 数据布局优化**（prefetch / SoA / 按 cell 重排 query） | 20~40% | 动 GridSearch 代码（当前冻结） |
| 合并 IJobParallelFor 的 Schedule+Complete | ~0.2% | 纯框架，收益小 |
| 上下文/HandleState 池化 | 微小 | 已有 BatchStorage 池 + RecycleState |
| 继续扫 guided k/floor | ~0 | k=4/floor=16 已是甜点，k=8 回归 |

## 3. 与 Unity 对比（为何不学它锁亲和/优先级）

- **Unity DOTS 不锁进程优先级**：JobWorker 线程正常优先级，仅前几毫秒 busy-spin；
  游戏跑在用户机器上，抢占式优先级会跟玩家前台程序抢时间片。
- **Unity 不固定核亲和**：worker 由 OS 调度，避免和渲染线程/主线程抢核；玩家 CPU 布局未知，硬编码反而害自己。
- **Unity 在这份负载上不会更快**：它的快来自 **ECS chunk 级连续布局**（带宽友好）；而 GridSearch 是
  空间哈希**随机 gather**（cell 平均 2.5 点，一个 cache line 都填不满），且布局冻结。
  调度层 Unity 用同样的不可分 batch + steal 模型，会撞同一个带宽地板。

### 3.1 为什么 GridSearch 不算 chunk 级连续布局

EntJoy 框架本身是 Archetype ECS（IJobChunk/ChunkJobData 走 chunk 路径，带宽友好），
**但 GridSearch 不经过 ECS chunk**：它是独立空间哈希网格（`NativeArray<float2>` 裸数组），走
`IJobParallelFor` → `ScheduleParallelFor`（guided 生效的那条路径）。其"cell 内连续"是**极短段**
（平均 2.5 点 ≈ 20 字节），每 query 随机跳 9 个 cell → 跨 cell 随机 gather，不是 Unity chunk 那种
长顺序遍历。这也是为什么 Unity 的布局优势在这里不成立。

## 4. 还有多少可挤

见 §2.2 表。**一句话**：调度已近地板（还能挤 ~3-5%，收益递减），真正的大头在数据布局，而它
被 GridSearch 冻结挡住。若解除冻结，prefetch（提前预取 9 个 cell 的 CellStartEnd + SortedPositions）、
SoA 化（X/Y 分离）、按 cell 重排 query（同 cell 邻域的 query 相邻 → tile 内局部性暴增）是三个方向。
